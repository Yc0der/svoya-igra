# Базовый игровой раунд — дизайн реализации

Продолжение [2026-08-03-svoya-igra-design.md](2026-08-03-svoya-igra-design.md), которое
уже фиксирует состояние-машину раунда, таймеры, правила фальстарта/ничьей, формат пакета
(дерево пакет → раунды → темы → вопросы) и разделение «участник vs счётчик». Этот документ
не повторяет то решение, а доводит его до конкретных типов, сообщений и границ модулей,
нужных для плана реализации.

Область: то, что перечислено в «Веха 1» исходной спеки за вычетом лобби (уже реализовано
walking skeleton'ом) — сетка, выбор, кнопка, голосование, счёт, итог. Звук на табло
сознательно отложен за пределы этой вехи (см. «Отклонения» ниже).

## Движок (`server/src/engine.ts`)

Чистая функция/класс без сети, диска и часов — на входе текущее состояние + событие, на
выходе новое состояние и список эффектов. Время приходит только как событие
`timer-expired`.

```ts
type Phase =
  | 'selecting' // ВЫБОР ВОПРОСА
  | 'question-open' // ВОПРОС ОТКРЫТ
  | 'buzzed' // НАЖАЛ
  | 'judging' // СУДЕЙСТВО
  | 'reveal' // РАСКРЫТИЕ
  | 'round-end' // КОНЕЦ РАУНДА
  | 'game-end'; // КОНЕЦ ИГРЫ

// Плоские массивы/объекты, а не Set/Map — EngineState целиком проходит через
// JSON.stringify в снапшоте комнаты, а Map/Set сериализуются в '{}'.
interface EngineState {
  pack: Pack;
  roundIndex: number;
  answeredQuestionIds: string[];
  phase: Phase;
  turnCounterId: string; // чей ход выбирать
  currentQuestion: { themeIndex: number; questionId: string } | null;
  buzzedCounterId: string | null;
  // Кто временно не может жать «Ответ» после своей же ошибки — НЕ здесь.
  // С 2026-08-05 (вторая правка) это не состояние движка вообще: движок не
  // знает, кто и когда был временно исключён, это решает Комната тем же
  // паттерном, что и фальстарт (design.md, «Комната»). См. «Отклонения»,
  // «Параллельная блокировка вместо грейс-таймера».
  votes: Record<string, boolean>; // counterId -> зачёт/незачёт
  scores: Record<string, number>; // counterId -> очки
  lastCorrectCounterId: string | null;
  hostId: string | null; // не counterId — ведущий не в scores. null = двое, открытое судейство
}

type TimerName = 'question' | 'said-answer' | 'vote' | 'reveal' | 'round-end';

type EngineEvent =
  | {
      type: 'select-question';
      counterId: string;
      themeIndex: number;
      questionId: string;
    }
  | { type: 'buzz'; counterId: string }
  | { type: 'said-answer'; counterId: string }
  | { type: 'vote'; counterId: string; correct: boolean }
  | { type: 'timer-expired'; timer: TimerName }
  | {
      type: 'adjust-score';
      requesterId: string;
      targetCounterId: string;
      delta: number;
    } // панель ведущего, requesterId сверяется с hostId внутри движка
  | { type: 'cancel-question'; requesterId: string };

type Effect =
  | { type: 'start-timer'; timer: TimerName; ms: number }
  | { type: 'cancel-timer'; timer: TimerName };

function reduce(
  state: EngineState,
  event: EngineEvent,
): { state: EngineState; effects: Effect[] };
```

Ничья в голосовании и «никто не проголосовал» — в пользу отвечающего (уже решено в
исходной спеке). «Кто выбирает следующий» — тот, кто последним ответил верно; если вопрос
не взял никто, выбирает тот же счётчик, что и в прошлый раз (`lastCorrectCounterId`
не меняется).

## Запуск игры из лобби

Новое сообщение клиент → сервер: `{ type: 'start-game' }`. Комната (не движок — до этого
момента `EngineState` не существует) проверяет минимум два участника, грузит пакет,
конструирует начальный `EngineState` (`phase: 'selecting'`, `turnCounterId` — случайный
участник, `roundIndex: 0`, счёт всех счётчиков — 0) и с этого момента начинает рассылать
`GameStateView` вместо лобби-состояния. «Начинает любой из них» — любой участник может
прислать `start-game`, без выделенного ведущего, как и решено в исходной спеке.

## Комната (расширяет `server/src/room.ts`)

`Room` — та же единственная «владелец правды» из исходной спеки, а не отдельный параллельный
класс: спека явно называет только два серверных модуля с логикой (Движок и Комната), заводить
третий ради игровых сообщений было бы лишней сущностью без причины. Комната переводит
клиентские сообщения в события движка, вызывает `reduce`, применяет
эффекты как настоящие `setTimeout`/`clearTimeout`, обновляет своё состояние и рассылает его
(существующий механизм `onChange`/`broadcastState` не меняется по форме, только по
содержимому payload'а).

**Фальстарт обрабатывается до движка.** Если `buzz` приходит, когда `phase !==
'question-open'`, комната не строит `EngineEvent` вообще — просто отвечает одному
виновному сокету транзитным сообщением `falsestart`, включающим клиентскую блокировку на
2 секунды. Так движок не должен знать про «недействительные» нажатия — это дешевле, чем
тащить их через машину состояний ради того, чтобы она их проигнорировала.

## Счётчик

Отдельный тип, не поле участника:

```ts
interface Counter {
  id: string;
  score: number;
}
```

Для Вехи 1 связь с участником один-к-одному максимально просто: `Counter.id ===
Participant.id`, отдельной таблицы соответствий нет. Сущности разные в коде (разные
типы, разные модули читают/пишут), но не в хранении — единственное место, которое
придётся тронуть при переходе к командам.

## Протокол — новые сообщения

Клиент → сервер:

```ts
| { type: 'select-question'; themeIndex: number; questionId: string }
| { type: 'buzz' }
| { type: 'said-answer' }
| { type: 'vote'; correct: boolean }
| { type: 'toggle-host' } // отметить/снять себя как ведущего — только в лобби, см. «Ведущий»
| { type: 'adjust-score'; participantId: string; delta: number } // панель ведущего
| { type: 'cancel-question' } // панель ведущего
```

Сервер → клиент (расширяет существующий broadcast состояния):

```ts
interface GameStateView {
  phase: Phase;
  roundIndex: number;
  grid: {
    themeName: string;
    questions: { id: string; price: number; answered: boolean }[];
  }[];
  turnParticipantId: string;
  currentQuestion: { text: string; price: number } | null; // без ответа до раскрытия
  buzzedParticipantId: string | null;
  // На judging видно только на reveal и — при hostId !== null — только тому
  // сокету, чей participantId === hostId. Иначе null. Из этого следует, что
  // GameStateView больше не одинаков для всех получателей одного и того же
  // состояния — см. «Персональные состояния» ниже.
  correctAnswer: { text: string; comment?: string } | null;
  // Не секрет ни от кого (в отличие от correctAnswer), видны всем одинаково.
  // Не поле движка — Room-состояние (design.md, «СУДЕЙСТВО», 2026-08-05,
  // «Параллельная блокировка»): временное исключение после неверного
  // ответа — транспортное ограничение, как фальстарт, не игровое правило.
  // Клиент дизейблит «Ответ» себе, когда graceExcludedParticipantId — его
  // собственный id, вместо молчаливого игнора нажатия.
  graceExcludedParticipantId: string | null;
  // ОТДЕЛЬНЫЙ от timerDeadline дедлайн: блокировка идёт параллельно уже
  // возобновившемуся отсчёту вопроса, а не вместо него — у них разные числа,
  // и клиент показывает оба независимо (два вызова useCountdown).
  graceExcludedUntil: number | null;
  timerDeadline: number | null; // абсолютный timestamp, не защищаемся от рассинхрона часов клиента дополнительно
  scores: { participantId: string; score: number }[];
}
```

Сообщение `state` (существующее, расширено): к `participants`/`game` добавлено
`hostParticipantId: string | null` — кто сейчас отмечен ведущим в лобби (или зафиксирован им
на время идущей партии).

Отдельные разовые сообщения: `{ type: 'falsestart' }` — только виновному сокету, не часть
общего состояния. `{ type: 'start-game-error'; reason: 'not-enough-players' | 'no-pack' |
'game-in-progress' | 'host-required' }` — только тому, кто прислал `start-game`; до этой
правки `Room.startGame()`'s результат никуда не долетал до клиента вообще, что было терпимо
при единственной практической причине отказа (мало игроков, и так видно по списку в лобби), но
перестало быть терпимым с появлением `host-required` — эта причина отказа не видна на глаз.

### Персональные состояния

До этой правки `broadcastState` в `server/src/server.ts` собирал один JSON и слал его
одинаковым всем открытым сокетам. Теперь `Room.toGameStateView(viewerId)` принимает
`participantId` смотрящего (или `null` для ещё не залогиненного сокета и для табло — оно
никогда не шлёт `join`), и `broadcastState` формирует сообщение отдельно на каждый сокет,
подставляя `connections.get(ws) ?? null`. Табло получает `viewerId = null` всегда — значит,
`correctAnswer` для него на `judging` в режиме с ведущим будет `null` так же, как для рядовых
игроков, и не нужно отдельной ветки «табло особый случай».

## Клиенты

**Табло (`/board`)** — сетка (закрашивает разобранные ячейки), **имя того, чей сейчас ход, во
время выбора вопроса** (исходная спека, «ВЫБОР ВОПРОСА»: «Остальные видят на табло, чей сейчас
ход» — легко потерять при кратком пересказе, поэтому здесь выписано отдельно), крупный текст
вопроса при открытии, имя нажавшего, результат и комментарий на раскрытии, live-счёт, при
`phase === 'game-end'` — итоговая таблица по местам. Ничего не отправляет — не меняется
относительно исходной спеки.

**Игрок (`/`)** — экран определяется фазой и тем, я ли `turnParticipantId` /
`buzzedParticipantId` / `hostParticipantId`:

| Фаза                                                                      | Я — ход/нажал/ведущий                                                      | Не я                     |
| ------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------ |
| `selecting`                                                               | Сетка тем/цен для выбора                                                   | «Сейчас выбирает Х»      |
| `question-open`, я не ведущий и не заблокирован                           | Большая кнопка «Ответ»                                                     | То же                    |
| `question-open`, я заблокирован (`graceExcludedParticipantId === selfId`) | Кнопка «Ответ» неактивна + «Ты уже пробовал(а) — жди Nс» (свой отсчёт)     | —                        |
| `question-open`, я ведущий                                                | «Вопрос открыт — ждём, кто нажмёт», без кнопки                             | —                        |
| `buzzed`, я нажал                                                         | «Скажи ответ вслух» + «Я ответил»                                          | «Х отвечает» (неактивно) |
| `judging`, `hostId === null`, не я отвечал                                | Кнопки «Зачёт»/«Незачёт» + отметка своего голоса после клика               | —                        |
| `judging`, `hostId === null`, я отвечал                                   | Жду результат                                                              | —                        |
| `judging`, `hostId !== null`, я ведущий                                   | Текст ответа + Кнопки «Зачёт»/«Незачёт» (`correctAnswer` виден только мне) | —                        |
| `judging`, `hostId !== null`, не ведущий                                  | «Ждём решения ведущего», без ответа и без кнопок                           | То же                    |
| `reveal`                                                                  | Правильный ответ, комментарий, обновлённый счёт (то же, что на табло)      | То же                    |
| `round-end`                                                               | Промежуточный счёт, «следующий раунд начинается»                           | То же                    |
| `game-end`                                                                | Итоговая таблица мест (то же, что на табло)                                | То же                    |

Фальстарт — локальная блокировка кнопки на 2с по сообщению `falsestart`, не завязана на
`phase` из общего состояния. Заблокированность по `graceExcludedParticipantId` — не
локальная, приходит с сервера и не привязана к конкретному клику (см. «Отклонения»,
«Параллельная блокировка вместо грейс-таймера»).

Ведущий видит ещё и постоянную панель управления (±очки, отмена вопроса) поверх любого из
этих экранов, в любой фазе — см. «Отклонения», «Панель ведущего».

**Табло на `judging` в режиме с ведущим** не показывает `correctAnswer` (он и не придёт —
персональные состояния, выше) — вместо ответа статус «Ведущий судит…», тот же по духу текст,
что уже используется для «Х жмёт кнопку».

## Формат пакета — конкретные типы

```ts
interface Pack {
  title: string;
  author: string;
  createdAt: string; // ISO-дата
  rounds: Round[];
}
interface Round {
  themes: Theme[];
}
interface Theme {
  name: string;
  questions: Question[];
}
interface Question {
  id: string;
  price: number;
  text: string;
  answer: string;
  comment?: string;
  type: 'обычный' | 'кот' | 'аукцион'; // движок Вехи 1 обрабатывает только 'обычный'
}
```

Файлы — в папке `packs/` рядом с приложением, без базы (уже решено в исходной спеке). Для
Вехи 1 без UI выбора пакета: сервер при старте грузит один фиксированный путь
(`packs/current.json`), валидирует по схеме; на ошибке — понятное сообщение в консоль вместо
падения (тот же принцип деградации, что уже применён к битому снапшоту комнаты).

Тестовый пакет на тему «Общая эрудиция» (2–3 раунда) пишется руками как часть этой вехи —
генератор пакетов остаётся Вехой 3.

## Тестирование

Как и в исходной спеке: юнит-тесты движка прогоняют целую партию за миллисекунды, включая
гонку нажатий (детерминированно — кто пришёл на сервер первым) и все таймауты. Интеграционные
тесты комнаты — настоящие WS-клиенты, обрыв/возврат по токену во время игры. Один E2E-сценарий
(Playwright): табло + два игрока разыгрывают два вопроса.

## Отказы

Ничего нового сверх уже решённого в исходной спеке: любое состояние с ожиданием человека
имеет таймаут, снапшот на диск переживает падение сервера, обрыв связи участника не роняет
его счёт/место в игре.

## Отклонения от исходной спеки

**Звук на табло отложен за пределы этой вехи.** Исходная спека называет звук важным для
атмосферы, но не включает его в перечисление «Веха 1» явно. Решение принято в брейнсторминге
2026-08-04: сфокусироваться на самой механике раунда сейчас, звук — отдельным дешёвым шагом
после того, как сыграна первая живая партия.

**Неверный ответ переоткрывает вопрос — с 2026-08-05, только в режиме с ведущим, сразу же и
с оставшимся временем, а не свежим таймером.** Само переоткрытие работает только когда
`hostId !== null` — см. следующий пункт, почему без ведущего оно снято совсем. Кто уже
пробовал и ошибся по этому вопросу, временно (5 секунд) не может нажать повторно — не
состояние движка, транспортное ограничение Комнаты, подробности в «Параллельная блокировка
вместо грейс-таймера» ниже.

Это решение прошло два промежуточных состояния в тот же день, каждое найдено следующей живой
проверкой, — стоит того, чтобы прочитать по порядку, а не только конечный результат:

1. Свежий полный `QUESTION_TIMER_MS`, а не буквальный остаток. Обоснование архитектурное
   (движок не знает часов, а буквальный остаток требует его знать) и опиралось на то, что
   «щедрее — не значит нечестно». Живая проверка показала, что это **ощущается как баг**:
   игрок видит один и тот же вопрос на экране, а отсчёт после неверного ответа прыгает
   обратно к полному значению.
2. Буквальный остаток, но **после** отдельного 10-секундного «грейс-таймера» (движковый
   таймер `reopen-grace`, отдельная фаза ожидания перед тем, как отсчёт вопроса возобновлялся).
   Чинило прыжок отсчёта, но вводило новую проблему того же рода: на вопрос в сумме уходило
   **больше** заявленных 30 секунд — грейс шёл ПЕРЕД возобновлением, а не одновременно с ним.
3. **Текущее решение:** буквальный остаток, возобновляется **в тот же момент**, что и вердикт
   — без какой-либо фазы ожидания между ними. Блокировка того, кто ошибся, идёт **параллельно**
   этому отсчёту (тем же механизмом, что и фальстарт — Комната, не движок), а не последовательно
   перед ним. Общее время на вопрос от количества ошибок больше не растёт вообще.

**Пауза «раскрытия» и пауза «конца раунда» получают собственные таймеры, которых нет в
таблице исходной спеки.** Таблица таймеров перечисляет только вопрос/ответ-вслух/голосование/
фальстарт, но правило «ни одно состояние не ждёт человека бесконечно — везде есть таймаут»
(исходная спека, раздел «Отказы») требует таймаута и здесь — иначе РАСКРЫТИЕ и КОНЕЦ РАУНДА
зависли бы без человека, нажимающего «дальше». Добавлены `reveal` (4000 мс — прочитать
результат) и `round-end` (5000 мс — прочитать промежуточный счёт перед сеткой следующего
раунда) как обычные именованные таймеры движка, наравне с остальными. Значения — того же
рода прикидка на глаз, что и у всех остальных таймеров исходной спеки, и так же помечены как
подлежащие правке после первой живой партии.

**Ничья/отсутствие голосов в судействе разрешаются единообразно через правило большинства.**
«За» ⩾ «против» → зачёт (это одновременно покрывает явную ничью и полное отсутствие голосов,
поскольку 0 ⩾ 0) — то же правило «в пользу отвечающего», сформулированное как одно условие
вместо двух отдельных частных случаев.

**Ведущий для 3+ игроков (2026-08-05) — не деталь реализации, а правка исходной спеки.**
Найдено на первой живой проверке, не в коде и не в тестах: любой, кто голосует в судействе, к
моменту голосования уже видел правильный ответ на табло. Переоткрытие кнопки «Жать!» после
«Незачёт» рассчитано именно на голосующих — то есть открывает вторую попытку тем, кто уже не
может ей честно воспользоваться, независимо от того, сколько всего человек в комнате: два,
три или шесть. Это не баг движка (он делает ровно то, что написано), а дыра в правиле из
спеки от 2026-08-03.

Рассмотренные варианты и почему выбран именно этот — подробно обсуждалось с человеком, ведущим
разработку, прежде чем менять код:

1. _Просто убрать переоткрытие везде._ Чинит дыру для любого числа игроков, ничего не ломает,
   не требует новой роли. Отклонено человеком, ведущим разработку: вторая попытка при 3+ — то,
   что выделяет живую «Свою игру», жертвовать ей не готовы.
2. _Прятать ответ от табло, показывать только устно._ Тогда голосующим нечем сверить
   сказанное — задача судейства не решается вообще без кого-то, кто знает ответ. Отклонено как
   нерабочее.
3. _Ведущий обязателен всегда, включая двоих._ Не решает ничего сверх варианта 4 при двух
   игроках (там голосующий и есть единственный потенциальный «второй нажимающий», прятать
   секрет больше не от кого), только добавляет обязательную третью роль там, где она не нужна.
4. **Выбрано: два раздельных режима по числу счётчиков.** Двое — открытое судейство, ответ
   виден всем, переоткрытия нет (вариант 1, но только для этого случая — при двух он ничего не
   отбирает, потому что переоткрывать всё равно было не для кого). Трое и больше — ответ видит
   только ведущий, отдельная непересчётная роль, переоткрытие работает как в исходной спеке.
   В итоге у минимального состава — простое правило без новой роли, а у целевой аудитории
   (3–6, design.md, «Для кого») — сохранён «перехват» ценой одного человека, не играющего этот
   раунд, что уже дёшево ложится на разделение «участник vs счётчик» (design.md).

Что изменилось в реализации: `EngineState.hostId` (`string | null`, не входит в `scores`),
`Room.hostParticipantId` + сообщение `{ type: 'toggle-host' }` в лобби, `startGame()` отказывает
кодом `host-required`, если счётчиков трое и больше, а ведущий не отмечен. Протокол стал
персональным (`Room.toGameStateView(viewerId)`) — подробности в разделе «Протокол — новые
сообщения» выше.

**Параллельная блокировка вместо грейс-таймера (2026-08-05, финальная версия судейства с
ведущим).** Три решения подряд в один день (нумерованный список выше, «Неверный ответ
переоткрывает вопрос») привели сюда: исключённый после ошибки блокирован 5 секунд
(`GRACE_EXCLUSION_MS`, снижено с исходных 10 по фидбэку с живой проверки), но эта блокировка
идёт **параллельно** уже возобновившемуся отсчёту вопроса, а не последовательно перед ним —
никакой отдельной фазы ожидания. Сдерживающий фактор — сам штраф («без него выгодно жать
всегда», design.md, «СУДЕЙСТВО»), пятисекундная блокировка не про честность, а про короткую
фору остальным.

Ключевое архитектурное решение: **эта блокировка — вообще не состояние движка**, а
транспортное ограничение Комнаты, тем же паттерном, что и фальстарт (design.md, «Комната»:
«Фальстарт обрабатывается до движка... комната не строит `EngineEvent` вообще»). Раньше
(промежуточная версия 2) она была именованным таймером движка (`reopen-grace`) с собственной
блокирующей фазой; убрана из движка вообще, а не просто ускорена, потому что параллельность
с ГЛАВНЫМ таймером вопроса — который движок эмитит как единое целое, `{ timer: 'question', ms
}`, — сама по себе требует второго, независимого отсчёта, а формат `Effect` рассчитан ровно на
один активный таймер за раз. Тащить эту параллельность в движок означало бы городить в нём
модель конкурентных таймеров ради единственного места, где она нужна — усложнение того самого
свойства, ради которого движок вообще сделан чистым.

Механизм (`server/src/room.ts`):

- `Room` хранит `graceExcludedCounterId: string | null` и `graceExcludedUntil: number | null` —
  не поля `EngineState`, обычные приватные поля класса, не переживающие перезапуск сервера
  (цена этого — максимум несколько секунд одной короткой блокировки после редкого падения
  ровно в эту секунду, не влияющих на исход партии; персистентность здесь того не стоит).
- `Room.dispatch()` определяет, что честный реопен только что произошёл, по самому переходу
  состояния — `buzzedCounterId` был кем-то и стал `null`, фаза была `'judging'` и стала
  `'question-open'` — а не по типу события: `resolveVote()` в движке достижим и явным
  сообщением `vote` от ведущего, и по истечении `VOTE_TIMER_MS` (движок отвечает мгновенным
  вердиктом «в пользу отвечающего» в обоих случаях одинаково). Обнаружив переход, Комната
  запоминает `buzzedCounterId` _до_ диспатча и заводит `graceExcludedUntil = Date.now() +
GRACE_EXCLUSION_MS`.
- `Room.buzz()`, тем же паттерном, что фальстарт, отвечает `'ok'` без диспатча в движок, если
  `participantId` совпадает с исключённым и `Date.now() < graceExcludedUntil` — не `'falsestart'`
  в ответе: это другой случай (не включает клиентскую 2-секундную локальную блокировку), клиент
  и так уже знает свой отсчёт из общего состояния.
- `Room.toGameStateView()` лениво «гасит» оба поля до `null` в возвращаемом значении, если
  `Date.now() >= graceExcludedUntil` — отдельного сброса по таймеру не требуется вообще.

Отдельно и без изменений с прошлой правки сохранился механизм **буквального остатка** для
самого таймера вопроса — `pendingReopenBudget: { questionId, remainingMs } | null`,
захватывается в `Room.buzz()` из `gameTimerDeadline - Date.now()`, подставляется в
`Room.applyEffects()` вместо `effect.ms`, когда движок эмитит `start-timer` для `'question'` с
тем же `currentQuestion.questionId`. Это не тот вариант, который отклонила самая первая
попытка («завести в Комнате отдельный учёт... прокидывать остаток обратно как параметр эффекта
**движку**») — здесь остаток никогда не попадает в движок, `Room` тихо подменяет число в уже
готовом эффекте, который сама же и исполняет через `setTimeout`; движок как был, так и остаётся
чистой функцией без единого обращения к времени. Поле `activeTimerName`, которое отличало
«тикает `question`» от «тикает `reopen-grace`» в промежуточной версии, упразднено вместе с
самим `reopen-grace` — различать больше нечего, пока идёт `question-open`, тикает всегда
именно `question`.

Восстановление из снапшота (`PHASE_TIMER` в конструкторе `Room`) упрощено обратно: раз в
движке больше нет отдельной грейс-фазы, отпала и специальная ветка для нее — восстановление
всегда просто `PHASE_TIMER[phase]`, как до появления ведущего.

**Панель ведущего: ±очки и отмена вопроса (2026-08-05, четвёртая правка того же дня).**
Найдено живой проверкой: судейство «зачёт/незачёт» — не всё, что нужно человеку, который
реально управляет вечером. Нужно уметь поправить счёт вручную (спорный случай, опечатка,
устный уговор компании) и закрыть кривой вопрос из пакета, не дожидаясь, пока кто-то на него
нажмёт и потратит впустую попытку.

Оба действия — новые события движка, доступные только `hostId`, тем же паттерном авторизации,
что уже есть у `vote` в режиме с ведущим (движок сам сверяет `requesterId === hostId`, Комната
не решает это за него):

```ts
| { type: 'adjust-score'; requesterId: string; targetCounterId: string; delta: number }
| { type: 'cancel-question'; requesterId: string }
```

`adjust-score` работает **в любой фазе**, не только во время судейства — ошибку в счёте
естественно захотеть поправить в любой момент, привязывать это к конкретной фазе было бы
искусственным ограничением. `cancel-question` переиспользует существующий `revealQuestion(state,
null)` — тот же путь, что и «никто не нажал за 30 секунд»: вопрос помечается отвеченным, очки не
начисляются, ход остаётся у того же счётчика, работает из любой фазы с открытым вопросом
(`question-open`/`buzzed`/`judging`).

На клиенте это не отдельный экран, а **постоянная панель**, которую ведущий видит поверх
обычного фазового экрана в любой момент партии (`Player.tsx`, `hostAdminPanel()`) — список
счётчиков с кнопками `−100`/`+100` у каждого, и кнопка «Отменить вопрос», видимая только пока
вопрос действительно открыт.

Протокол: `{ type: 'adjust-score'; participantId: string; delta: number }` и `{ type:
'cancel-question' }` — без `requesterId` в сообщении от клиента, сервер сам подставляет реальный
`participantId` подключения (`connections.get(ws)`), не доверяя утверждению клиента о своей
роли.
