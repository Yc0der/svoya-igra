# Генератор пакетов — дизайн (Веха 3)

Реализация «Веха 3 — генератор пакетов» из
[2026-08-03-svoya-igra-design.md](2026-08-03-svoya-igra-design.md) («Порядок работ»). Спека там
фиксирует только архитектурный принцип: «Единственное место в проекте, которое ходит в интернет.
Пишет файл на диск — и на этом связь с игрой заканчивается». Этот документ решает, чем конкретно
оказывается «генератор».

## Решение: не автоматический пайплайн, а skill

Рассматривались два подхода:

1. **Отдельный скрипт/сервис**, который сам ходит в Anthropic API по ключу и пишет файл.
2. **Skill Claude Code** (`.claude/skills/pack-generator/`), который выполняется прямо в диалоге —
   человек просит, Claude генерирует и пишет `packs/<slug>.json` в этой же сессии.

Выбран **вариант 2**. Причины:

- **Деньги.** Подход 1 требует отдельного API-ключа и платит за каждый вызов из кармана
  пользователя отдельно от уже оплаченной подписки на Claude Code. Подход 2 использует уже
  оплаченную подписку — генерация пакета ничего не стоит сверх неё.
- **Интерактивность.** Часть процедуры ниже требует переспросить человека (финальные темы без
  уверенной идеи, темы вообще не названы) — это естественно для диалога и неестественно для
  скрипта, который дергает API один раз и получает единственный ответ.
- **Принцип «Генератор — единственное место, которое ходит в интернет» соблюдён так же** —
  Claude Code сам не хранит собственное состояние комнаты и не связан с игровым сервером; пишет
  файл на диск, и это единственная точка соприкосновения, как и было задумано.

Рассматривалась и генерация через реальный вызов Anthropic API (`@anthropic-ai/sdk`, structured
outputs по JSON-схеме `Pack`) — отклонено на этом этапе именно из-за пункта «деньги»: пользователь
явно предпочёл не заводить отдельный платный контур ради задачи, которую и так решает его текущая
подписка. Если это когда-нибудь понадобится (например, для автоматизации без участия человека) —
это отдельная веха, не пересмотр этой.

Отдельно рассматривалась внешняя зависимость `grill-me`
([mattpocock/skills@grill-me](https://skills.sh/mattpocock/skills/grill-me), 802K+ установок) для
интервью о темах — отклонено: это общий скилл «безжалостного интервью для заострения плана»,
заточенный под продуктовые/технические решения, а не под конкретно «узнать интересы гостей
вечеринки». Тащить внешнюю зависимость ради узкой задачи, которую скилл ниже решает сам парой
обычных вопросов, признано избыточным.

## Вход и вызов

Skill вызывается в обычном диалоге Claude Code, не как автономный CLI. Вход — свободный текст:
список желаемых тем основного раунда и, опционально, желаемая сложность.

**Если темы не названы явно** — Claude задаёт несколько обычных уточняющих вопросов: кто будет
играть, чем эти люди увлекаются — и сам выводит темы из ответов. Это часть процедуры самого
скилла, не отдельный скилл и не вызов внешнего инструмента.

**Сложность** — необязательный параметр. Если не задана, Claude подбирает её сам так, чтобы цена
вопроса реально соответствовала его трудности (см. «Содержательные правила» ниже), а не была
произвольной меткой.

## Форма пакета по умолчанию

Стандартный размер, ориентир — уже сыгранный `packs/current.json` (2 раунда × 4 темы × 4 вопроса),
увеличенный до:

- **2 раунда**, в каждом **5 тем × 5 вопросов**, цены `100/200/300/400/500`.
- Если человек назвал меньше 10 тем на весь основной раунд (2 × 5) — недостающие темы Claude
  добирает сам, смежные с уже названными.
- Число раундов **не** параметризуется пользователем на этом этапе — фиксировано на 2, тем же
  способом, каким сейчас зафиксирован размер `4×4` в реальном пакете. Если окажется мало — это
  отдельная правка позже, не блокирует веху.

### Финальный раунд

Правила самого финала (отсев тем, ставки, судейство) уже целиком реализованы в
[2026-08-05-final-round-design.md](2026-08-05-final-round-design.md) — генератор отвечает только за
`final.themes`, из которых игроки отсеивают все, кроме одной.

- **Минимум 10 тем-кандидатов** — заметно больше, чем в текущем `packs/current.json` (там всего 3),
  чтобы отсев был содержательным при любом числе игроков.
- Источник тем: сначала темы, уже использованные в основном раунде, затем смежные к ним. Если по
  конкретной теме нет уверенной идеи хорошего финального вопроса — Claude предлагает варианты
  человеку вместо того, чтобы всё равно сочинить вопрос похуже.

## Содержательные правила генерации

Это не проверяется валидатором — это то, чему Claude следует сам при формулировке вопросов:

- **Цена соответствует трудности.** Вопрос за 100 — узнаваемый и лёгкий, за 500 — специфический и
  трудный. Цена — не случайная метка поверх произвольного по сложности вопроса.
- **Без повторов внутри пакета.** Один и тот же факт/ответ не должен всплывать в двух разных
  вопросах пакета (реальный риск при нескольких вопросах на одну тему).
- **Тип вопроса — всегда `обычный`.** Поле `type` в схеме уже поддерживает `кот`/`аукцион`
  (design.md, «Формат пакета»), но игровой движок не реализует эти механики до вех 4 и 5
  соответственно — генератор вопросов таких типов сейчас создавал бы нерабочий контент.
  **Важно на будущее:** `ideas.md` («Кот в мешке») уже фиксирует это как зависимость в обратную
  сторону — «Требует раньше: … работающий генератор, который умеет помечать вопрос как кота». Это
  значит, что веха 4 не заканчивается изменениями в движке — этот же skill (`pack-generator`)
  тоже придётся доработать, чтобы он начал проставлять `type: 'кот'` (и позже `'аукцион'` для
  вехи 5). Не забыть при планировании вех 4/5.
- **Без медиа-вопросов.** Картинки/аудио/видео — записанная идея
  ([ideas.md](../../ideas.md), «Медиа-вопросы»), не веха 3: генератор не может легально достать
  медиафайл под конкретный вопрос, это открытая проблема самой идеи, а не то, что можно тихо решить
  здесь.
- **Без памяти и обучения на прошлых партиях.** Раздел ideas.md «Память и обучение генератора» —
  сознательно отдельная, более поздняя веха. Эта версия генератора не знает, как прошли предыдущие
  игры, и не подстраивается под них.

## Идентификаторы и формат

Конвенция id взята из уже существующего `packs/current.json`, чтобы не вводить вторую параллельную
схему:

- Обычный вопрос: `r{номер_раунда}-{slug_темы}-{цена}`, например `r1-geo-100`.
- Финальный вопрос: `final-{slug_темы}`, например `final-myth`.

`slug_темы` — тема, транслитерированная/сокращённая до короткого латинского идентификатора (как
`geo` для «Географии», `myth` для «Мифологии» в реальном пакете). Требование — уникальность id
внутри пакета, не глобальная стабильность между разными сгенерированными пакетами (design.md,
инвариант 3, требует стабильности id для будущей истории сыгранного — генератор соблюдает это
per-pack, кросс-паковая дедупликация id не нужна, потому что пакеты не смешиваются в одной партии).

`title`/`author`/`createdAt` — Claude заполняет сам: `title` по смыслу тем, `author` — что-то вроде
«сгенерировано pack-generator», `createdAt` — дата генерации.

## Запись и проверка

Пишет в **новый файл** `packs/<slug>.json`, где `<slug>` — короткое имя по смыслу тем (например
`packs/sport-kino-muzyka.json`). **`packs/current.json` не трогается** — это файл, который реально
читает запущенный сервер (`server/src/index.ts`, `PACK_PATH`) при старте, и его молчаливая
перезапись могла бы сломать уже идущую или подготовленную к вечеру партию.

Как сгенерированный пакет становится тем, во что реально играют — **не часть этой вехи**. Ручное
переименование/копирование поверх `current.json` было отклонено при ревью спеки как неудобное
решение: генератор должен делать пакеты проще, а не заменять один ручной шаг («написать JSON в
блокноте») другим («скопировать файл руками»). Правильное решение — выбор пакета прямо в
интерфейсе (скорее всего в уже существующей админ-панели), но это отдельные изменения сервера
(сейчас пакет грузится один раз при старте и не меняется — `Room` не умеет подменить его на лету) и
клиента, не касающиеся генератора вообще. Это отдельный дизайн-цикл (спека → план → TDD), не довесок
к вехе 3 — см. следующий шаг после этой спеки.

Сразу после записи Claude **обязан** прогнать файл через уже существующий валидатор —
`validatePack(data: unknown): Pack` из `server/src/pack.ts` (синхронная чистая функция, кидает
исключение с сообщением на невалидных данных). Практически — маленький одноразовый Node/tsx-запуск,
импортирующий `validatePack` и вызывающий его на распарсенном JSON только что записанного файла. Не
проходит — Claude чинит и перепроверяет тем же способом, не отдаёт как результат файл, который сам
не проверил.

## Файлы, которые появляются в этой вехе

- `.claude/skills/pack-generator/SKILL.md` — сама процедура: вход → уточняющие вопросы (если нужно)
  → генерация основного раунда → генерация кандидатов финала → запись файла → `validatePack` →
  починка при ошибке → отчёт человеку.
- Ничего не меняется в `server/`, `client/`, движке или протоколе — это инвариант данного решения
  (см. «Решение: не автоматический пайплайн, а skill» выше): генератор — целиком за пределами
  игрового рантайма.

## Тестирование

Обычный TDD (юнит-тесты на функции) здесь неприменим впрямую — «функция» это не код, а процедура,
которой следует Claude в диалоге. Проверка вехи вместо этого:

- **Прогон валидатора** — не отдельный новый тест, а тот же `validatePack`/`loadPack`, что уже
  покрыт тестами в `server/src/pack.test.ts`; для генератора это шаг процедуры, а не новый код,
  который нужно тестировать отдельно.
- **Контрольная генерация** — как часть плана, сгенерировать реальный пример пакета по вымышленному
  запросу (несколько тем + сценарий «темы не названы, отвечаю на уточняющие вопросы» +
  сценарий «фактически мало тем, генератор добирает сам») и убедиться, что результат проходит
  валидатор и читается как нормальный пакет вопросов при живом просмотре.
- Живая партия по сгенерированному пакету всё равно обязательна — правило «веха не закрыта без
  настоящей партии с живыми людьми» (`svoya-igra-dev`, шаг 7) действует одинаково для всех вех, не
  только для вехи 1. Здесь это естественно совпадает с ещё не сыгранной живой партией по вехе 2
  (финал со ставками, PR #11) — один и тот же вечер закрывает обе: играется по-настоящему
  сгенерированным этим скиллом пакетом, значит проверены и правила финала, и годность содержимого,
  сочинённого генератором, разом.

## Отказы

**Сгенерированный вопрос не проходит `validatePack`.** Claude чинит и перепроверяет сам, не
отдаёт невалидный файл как результат (см. «Запись и проверка»).

**Человек не может назвать темы.** Скилл сам задаёт уточняющие вопросы про состав играющих и их
интересы (см. «Вход и вызов») — это часть штатного сценария, не исключительная ситуация.

**Нет уверенной идеи для конкретной финальной темы.** Claude предлагает варианты человеку вместо
того, чтобы сочинить вопрос похуже (см. «Финальный раунд») — тоже штатный сценарий, не отказ.
