# Редактор пакетов — список для просмотра и жалобы на вопрос

Продолжение Вехи A ручного редактора пакетов (`docs/superpowers/specs/2026-08-15-pack-editor-a-design.md`).
После живой проверки Вехи A выяснилось: кликать по каждой цене в сетке, чтобы увидеть один
вопрос, неудобно, если цель — не точечная правка, а пробежаться глазами по всему пакету и
заметить странные вопросы (см. `docs/ideas.md`, «Список пакета для беглого просмотра»).

Эта веха добавляет два независимых, но связанных куска:

1. **Второй вид редактора — список**, где весь пакет виден сразу текстом, без кликов по сетке.
2. **Жалоба на вопрос** — кнопка у каждого вопроса в списке, открывающая окно с текстом «что не
   понравилось». Жалоба автоматически подтягивает контекст вопроса (текст, ответ, тема, цена) и
   сохраняется в файл, который `pack-generator` уже читает перед каждой генерацией — так
   ведущему не нужно вручную пересказывать генератору, что было не так.

## Правило

В уже существующем режиме редактирования пакета (`Admin.tsx`, там же, где сейчас сетка
«раунды → темы → цены») появляется переключатель вида — radio-баттоны «Сетка» / «Список», сразу
под кнопкой «Готово». Локальный React-стейт, не переживает выход из редактора (не персистится).

**По умолчанию открывается «Список»** — раз именно он и был запрошен для беглого просмотра,
это и есть основной сценарий входа в редактор. «Сетка» остаётся без изменений — она нужна,
когда уже точно знаешь, какой вопрос править.

Переключение вида закрывает любую открытую панель (форму правки или панель жалобы) — кнопка
«Пожаловаться» существует только в списке (см. ниже), так что при уходе в «Сетку» ей всё равно
негде было бы остаться видимой; форма правки закрывается для симметрии, чтобы переключение
вида было предсказуемым «чистым» действием в обе стороны, а не сохраняло состояние одного вида
поверх другого.

**Список.** Вопросы сгруппированы по раунду → теме (те же заголовки, что уже рисует сетка),
каждая строка — одна строка списка: цена, текст вопроса, кнопка «Пожаловаться» справа. Ответ и
комментарий в списке не показываются — задача списка увидеть сами вопросы одним взглядом, не
проверить правильность ответа (для этого уже есть форма правки).

Клик по строке (кроме кнопки «Пожаловаться») открывает ту же форму правки, что уже открывает
клик по цене в сетке, — `editingQuestionId` не завязан на то, из какого вида был клик.

**Панель жалобы.** Клик «Пожаловаться» открывает под списком панель с одним полем — `<textarea>`
для текста жалобы — и кнопками «Отправить»/«Отмена». Панель жалобы и форма правки
взаимоисключающие: открытие одной закрывает другую (тот же принцип, что уже разделяет
«редактировать» и «удалить» в форме правки — одно действие видно за раз).

«Отправить» неактивна на пустом/пробельном тексте — тот же клиентский guard, что уже есть у
«Сохранить» в форме правки (`isValidForm`).

Кнопка «Пожаловаться» **только в списке**, не в сетке — жалоба это часть беглого просмотра, а
не точечной правки, и дублировать её в обоих видах не нужно (можно переключиться на список,
благо переключатель виден в любой момент).

## Хранение и формат жалобы

Жалобы копятся в новом разделе в конце `docs/pack-generator-profile.md` —
`## Жалобы из ручного редактора`, последним разделом файла (после уже существующего
«Автособранное»). Сервер сам подставляет контекст вопроса — текст, ответ, тема, цена, файл и
название пакета; от человека нужен только текст самой жалобы.

Формат одной записи (добавляется в конец файла при каждой жалобе):

```markdown
- **2026-08-15, «Общая эрудиция» (sport.json), тема «Спорт», вопрос за 300:**
  «текст вопроса…» (ответ: «ответ») — не понравился, потому что…
```

Дата — календарная (`YYYY-MM-DD`), без времени: этого достаточно, чтобы через месяц понять,
когда жалоба появилась, а лишняя точность не нужна. Это не движковый код — сервер уже читает
системные часы в других местах (например, `network.ts`, WS ping/pong), инвариант «движок не
знает про часы» относится к `engine.ts`, не к серверной инфраструктуре.

Запись в файл — атомарная, тот же паттерн temp-файл + rename, что уже есть в `snapshot.ts` и в
`packs.ts` (Веха A). Отдельная от записи пакетов очередь сериализации (`withProfileWriteLock`,
по образцу уже существующего `withPackWriteLock` из Вехи A) — то же самое, что решило гонку при
двух правках вопроса подряд: без неё быстрая повторная жалоба (двойной клик «Отправить») могла
бы читать файл до того, как первая жалоба дописалась, и потерять одну из двух записей.

Если раздела `## Жалобы из ручного редактора` в файле ещё нет (самая первая жалоба за всё
время) — сервер добавляет заголовок раздела перед первой записью.

## pack-generator

Шаг 0 в `.claude/skills/pack-generator/SKILL.md` дополняется: читать новый раздел наравне с
«Ручными заметками» (`docs/pack-generator-profile.md`).

Если урок из жалобы уже обобщён в «Ручные заметки» (та же логика, что уже применяется к
разбору сгенерированных паков) — при следующей генерации перенести обобщение в «Ручные
заметки» и убрать уже учтённую сырую жалобу из раздела «Жалобы из ручного редактора», чтобы
список не рос одинаковыми повторами до бесконечности. Это правка промпта (SKILL.md), не кода —
перенос делает сам генератор (то есть Claude на Шаге 0), не отдельный механизм.

## Протокол и сервер

Новое сообщение и ответы — тот же паттерн, что и `admin-update-question`/`admin-pack`/
`admin-pack-error` из Вехи A, но с собственным типом ответа, чтобы ошибка жалобы не путалась с
ошибкой правки вопроса (у них разное отображение на клиенте — жалоба не трогает
`editedPack`/`editedPackError`):

```ts
| { type: 'admin-report-question'; filename: string; questionId: string; complaint: string }
```

```ts
| { type: 'admin-report-ack'; filename: string; questionId: string }
| { type: 'admin-report-error'; filename: string; questionId: string; reason: string }
```

Обработчик (`server.ts`, рядом с уже существующими `admin-*-question` хендлерами):

1. Тот же `basename(filename) !== filename` guard, тихий no-op при провале — тот же паттерн,
   что у всех остальных `admin-*` хендлеров, работающих с именем файла пакета.
2. `loadPack(join(packsDir, filename))` — свежее чтение с диска, не доверяем тому, что было в
   памяти клиента.
3. Найти вопрос по `questionId` (та же схема поиска по всем раундам/темам, что уже есть в
   Вехе A) — заодно возвращает тему и цену для текста записи. Не найден → `admin-report-error`
   («вопрос с таким id не найден»).
4. Сформировать запись (см. формат выше) и дописать в `docs/pack-generator-profile.md` через
   `withProfileWriteLock`.
5. Успех → `admin-report-ack`. Ошибка записи на диск → `admin-report-error` с текстом ошибки.

Путь к файлу профиля передаётся в `createServer` новой опцией `profilePath` — тот же принцип,
что уже применён к `packsDir`/`clientDistPath` (`index.ts` собирает путь через
`process.env.PROFILE_PATH ?? './docs/pack-generator-profile.md'`).

## Клиент

`useAdminConnection.ts` получает новый метод `reportQuestion(filename, questionId, complaint)`
и состояние `reportError: string | null` (по аналогии с `editedPackError`, но отдельное —
жалоба не должна тушить и не должна тухнуть от ошибки правки вопроса, это независимые действия).
Успешная жалоба (`admin-report-ack`) ничего не меняет в `editedPack` — панель жалобы просто
закрывается на клиенте после подтверждения.

`Admin.tsx` получает: `viewMode: 'grid' | 'list'` (локальный стейт, по умолчанию `'list'`),
`complainingQuestionId: string | null` и `complaintText: string` для панели жалобы. Открытие
панели жалобы сбрасывает `editingQuestionId` в `null` и наоборот — открытие формы правки (клик
по строке/цене) сбрасывает `complainingQuestionId`.

## Тестирование

**Сервер** (`packs.test.ts`/`server.test.ts`/новый `generatorProfile.test.ts`):

- Новый модуль `server/src/generatorProfile.ts` (`appendComplaint`) тестируется отдельно от
  сети, как и `packs.ts` в Вехе A: запись в первый раз создаёт раздел, повторная запись
  добавляет запись под уже существующим разделом, не трогая остальной файл.
- `server.test.ts`: `admin-report-question` на существующий вопрос дописывает файл на диске
  (читать напрямую, не через ответ сервера); на несуществующий `questionId` —
  `admin-report-error`, файл не тронут; path-traversal `filename` — тихий no-op, тот же
  паттерн доказательства через легитимное сообщение после.

**Клиент** (`Admin.test.tsx`):

- Переключатель показывает список по умолчанию при входе в редактор пакета.
- Клик по radio «Сетка» показывает сетку, обратно показывает список.
- В списке клик по строке (не по «Пожаловаться») открывает форму правки с текущими значениями
  вопроса.
- Клик «Пожаловаться» открывает панель, форма правки (если была открыта) закрывается.
- «Отправить» неактивна на пустом тексте.
- Успешная отправка закрывает панель жалобы.
- Ошибка отправки показывает текст ошибки, панель остаётся открытой.

## Отказы

**Пустая или пробельная жалоба.** Не отправляется — кнопка неактивна, тот же клиентский guard,
что у формы правки. Серверной проверки на пустоту нет — если каким-то образом дойдёт пустая
строка, она просто дописывается как есть; не стоит городить серверную валидацию ради
клиентского UI-ограничения, которое и так не даёт нажать кнопку.

**Жалоба на вопрос, который тем временем удалили или изменили другим способом.** Не
обрабатывается специально: сервер читает файл заново на каждой жалобе (см. «Протокол и
сервер», п.2) — если вопрос успели удалить, жалоба получит `admin-report-error` («вопрос не
найден»), как и любая другая операция над пропавшим id.

**Разрастание раздела жалоб без разбора.** Не автоматизируется в этой вехе — разбор и перенос
в «Ручные заметки» делает генератор на Шаге 0 (см. «pack-generator» выше), это уже
существующий процесс без нового кода, не гарантия, что жалобы не могут накопиться между
генерациями — это осознанно: генератор запускается не каждый день, и то, что жалоба полежит
до следующего запуска, не вредит.
