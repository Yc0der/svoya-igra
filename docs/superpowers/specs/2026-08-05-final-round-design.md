# Финал со ставками — дизайн реализации

Продолжение [2026-08-03-svoya-igra-design.md](2026-08-03-svoya-igra-design.md) (Веха 2, «Финал со
ставками» — см. «Порядок работ») и [2026-08-04-base-round-design.md](2026-08-04-base-round-design.md),
который довёл до реализации базовый раунд и добавил роль ведущего. Этот документ делает то же для

Зерно идеи уже было записано в [ideas.md](../../ideas.md), «Финал со ставками»: «Убираем темы по
одной, каждый тайно ставит часть своих очков и пишет ответ текстом». Здесь это доводится до
состояния-машины.

## Правила финала

Ровно **один** финальный вопрос, не несколько подряд. Классическая схема «Своей игры» — отсев тем
до одной — самодостаточная кульминация; несколько вопросов подряд усложняют реализацию (нужно
решать, откуда брать темы для второго и третьего раунда отсева) ради выгоды, которая не была
запрошена.

**Отсев тем.** Все счётчики по очереди вычёркивают по одной теме, пока не останется одна. Порядок
хода — **по возрастанию счёта**, как в оригинале: у кого меньше очков, тот вычёркивает первым, при
равенстве — по порядку, в котором был сформирован список счётчиков. Если тем меньше, чем нужно для
того, чтобы каждый счётчик вычеркнул минимум по одной, круг просто останавливается на единственной
оставшейся — не все успевают походить, и это нормально.

**Ведущий в финале обязателен всегда, даже при двоих счётчиках.** Это меняет правило, действовавшее
в базовом раунде: там ведущий нужен только с трёх счётчиков и выше, потому что при двоих
единственный не отвечавший голосует сам. В финале отвечают **все** счётчики одновременно — не
отвечавших не остаётся, голосовать некому в принципе, и это не зависит от того, сколько всего
играющих. Раз ведущего может физически не быть (комната ровно из двух человек, третьего устройства
нет), это создаёт видимый конфликт с уже существующим стартовым правилом (двое стартуют без
ведущего). Разрешение — намеренно **не** менять правило старта партии: если партия дошла до конца
последнего обычного раунда, а `hostId === null` (то есть партия шла на двоих без ведущего) — финал
**пропускается**, игра сразу заканчивается по результатам обычных раундов. То же самое, если в
пакете вообще нет `final`. Ничего не ломается: партия на двоих без ведущего играется от начала до
конца ровно так же, как сейчас, просто без кульминации, которую физически некому честно вести.
Компания, которая хочет финал, добавляет третьего человека (даже не играющего — только с
устройством) и отмечает его ведущим в лобби, как и для базового раунда с 3+ счётчиками.

**Ставка.** Тайная, каждый видит только свою. Максимум — текущий счёт счётчика; если счёт `≤ 0`,
играть можно только на `0` — терять уже нечего, но и заработать без реального ответа тоже. Ставка
делается **зная только название оставшейся темы**, не сам вопрос — как в оригинале: азарт ставки на
свои знания по теме, а не расчёт после того, как увидел вопрос.

**Ответ.** Текстом, все одновременно, время даётся заметно больше, чем на устный ответ в обычном
раунде — набор текста на телефоне медленнее речи.

**Тайм-ауты.** Не успел поставить ставку — `0`. Не успел написать ответ — пустая строка,
засчитывается как неверный (если ставка была ненулевой — она сгорает). Никакой отдельной «скидки»
за пропущенный ответ нет: правило «в пользу отвечающего» из design.md относится к спорному
голосованию, а не к простому «не успел».

**Судейство.** Ведущий видит все ставки и ответы разом, как только все прислали (или истёк общий
таймер) — не по одному в порядке отсева, а списком, отмечает верно/неверно по каждому в любом
порядке. Когда отмечены все (или истёк таймер, тогда неотмеченным — незачёт по умолчанию, тем же
принципом, что и пропущенный ответ: непроверенное не считается доказанно верным) — очки
применяются разом: зачёт → `+ставка`, незачёт → `−ставка`.

## Формат пакета — новое поле `final`

```ts
export interface FinalTheme {
  name: string;
  question: {
    id: string;
    text: string;
    answer: string;
    comment?: string;
  };
}

export interface Pack {
  title: string;
  author: string;
  createdAt: string;
  rounds: Round[];
  final?: { themes: FinalTheme[] };
}
```

`final` необязателен — старые пакеты и пакеты без финала не ломаются, после последнего обычного
раунда партия идёт сразу в `game-end`, как и сейчас. У финального вопроса нет `price` (в финале цену
задаёт ставка) и нет `type` (механики «кот»/«аукцион» к финалу неприменимы). `question.id`
по-прежнему участвует в общей проверке уникальности id по всему пакету
(`checkUniqueQuestionIds`) — тот же принцип, что и у обычных вопросов: движок и клиент используют id
как стабильный ключ.

Валидация (`pack.ts`): `final.themes` — массив минимум из **двух** элементов (меньше — отсеивать
нечего, вырожденный случай «сразу одна тема» не через что пройти естественным путём, проще запретить
на загрузке, чем городить обход этого случая в движке); каждый элемент — `name` (непустая строка) и
`question` с `id`/`text`/`answer` (обязательные) и `comment` (опционально) — переиспользует бо́льшую
часть `validateQuestion`, но без полей `price`/`type`.

## Движок (`server/src/engine.ts`)

Расширяется тот же движок, а не отдельный модуль — согласуется с уже установленным в проекте
принципом («Комната и Движок — единственные модули с логикой», design.md, «Архитектура») и с тем, как
уже был добавлен ведущий: новые `Phase`, поля `EngineState`, события, эффекты в том же файле, без
новых файлов. Рассмотренная альтернатива — отдельная под-машина состояний для финала (`ideas.md`
заранее резервирует этот подход для аукциона, где реально есть ветвление: шаг ставки, ва-банк, пас).
Поток финала линейный (отсев → ставки → ответы → суд → раскрытие) без циклов и ветвлений сверх этого
— выделять его в отдельный модуль означало бы городить стык между двумя движками ради изоляции,
которая здесь не нужна.

```ts
export type Phase =
  | 'selecting'
  | 'question-open'
  | 'buzzed'
  | 'judging'
  | 'reveal'
  | 'round-end'
  | 'final-elim'
  | 'final-wager'
  | 'final-answer'
  | 'final-judging'
  | 'final-reveal'
  | 'game-end';

export type TimerName =
  | 'question'
  | 'said-answer'
  | 'vote'
  | 'reveal'
  | 'round-end'
  | 'final-elim'
  | 'final-wager'
  | 'final-answer'
  | 'final-judging'
  | 'final-reveal';
```

Новые поля `EngineState` — `null`/пустые, пока финал не начался:

```ts
finalRemainingThemeIndices: number[] | null; // индексы в pack.final.themes, ещё не вычеркнутые
finalElimCounterId: string | null;    // чей ход вычёркивать
finalThemeIndex: number | null;       // осталась одна — эта
finalWagers: Record<string, number>;  // counterId -> ставка
finalAnswers: Record<string, string>; // counterId -> текст ответа
finalVerdicts: Record<string, boolean>; // counterId -> вердикт ведущего, заполняется частями
```

Новые события:

```ts
| { type: 'eliminate-final-theme'; counterId: string; themeIndex: number }
| { type: 'submit-wager'; counterId: string; amount: number }
| { type: 'submit-final-answer'; counterId: string; text: string }
| { type: 'final-vote'; requesterId: string; counterId: string; correct: boolean }
```

**Переход в финал.** `afterReveal()` сейчас при `roundIndex + 1 >= pack.rounds.length` безусловно
уходит в `game-end`. Условие расширяется: если `pack.final` есть **и** `state.hostId !== null` —
`final-elim` (с `finalRemainingThemeIndices` = все индексы тем, `finalElimCounterId` = счётчик с
минимальным `scores` по порядку ключей). Иначе — как раньше, сразу `game-end`.

**`final-elim`.** `eliminate-final-theme` валиден только от `finalElimCounterId` и только для ещё не
вычеркнутого `themeIndex`. Убирает индекс из `finalRemainingThemeIndices`; если остался не один —
ход переходит к следующему счётчику по тому же порядку возрастания счёта (circular); если остался
один — фиксируется `finalThemeIndex`, переход в `final-wager`. Таймер `final-elim` на каждый ход;
истёк — вычёркивается случайная из оставшихся тем тем же кодом, что и ручной выбор (не отдельная
ветка).

**`final-wager`.** `submit-wager` пишет в `finalWagers[counterId]`, зажимая `amount` в
`[0, max(0, scores[counterId])]` — движок не доверяет клиентскому числу. Когда `finalWagers`
покрывает всех счётчиков **или** истёк таймер `final-wager` — недостающим ставится `0`, переход в
`final-answer`.

**`final-answer`.** `submit-final-answer` пишет в `finalAnswers[counterId]`. Та же логика «все или
таймер»; недостающим — `''`. Переход в `final-judging`.

**`final-judging`.** `final-vote` валиден только от `hostId`, пишет `finalVerdicts[counterId]` —
**не** переводя фазу немедленно (в отличие от `judging` базового раунда, где ведущий одним голосом
решает сразу) — ведущий размечает всех в любом порядке, необязательно за один вызов. Когда
`finalVerdicts` покрывает всех счётчиков **или** истёк таймер `final-judging` — недостающим `false`,
затем очки применяются разом (`correct ? scores[id] + wager : scores[id] - wager` для каждого
счётчика) и происходит переход в `final-reveal` (с собственным эффектом `start-timer('final-reveal',
FINAL_REVEAL_TIMER_MS)` — не переиспользуем таймер `reveal` обычного раунда: там читают одну строку
ответа, здесь — таблицу ставок/ответов/вердиктов по всем счётчикам, времени нужно заметно больше). По
истечении `final-reveal` — безусловно `game-end`. Следующего раунда после финала не бывает независимо
от `pack.rounds` — финал всегда terminal.

## Комната (`server/src/room.ts`)

Изменения тоньше, чем в движке — тот же принцип, что и раньше: Комната только переводит сообщения в
события и рассылает состояние, всю игровую логику несёт движок.

- `PHASE_TIMER` пополняется записями для всех пяти новых фаз. Значения — прикидка на глаз, как и
  остальные таймеры проекта (design.md: «будут меняться после первой живой игры»):
  `final-elim` 20 000 мс, `final-wager` 20 000 мс, `final-answer` 45 000 мс (набор текста на
  телефоне ощутимо медленнее устной речи), `final-judging` 60 000 мс (ведущему нужно прочитать все
  ответы, не одну строку), `final-reveal` 10 000 мс (итоговая таблица по всем счётчикам, дольше
  обычного `REVEAL_TIMER_MS` = 4000 мс).
- Новые тонкие методы-обёртки, зеркалящие уже существующий паттерн (`selectQuestion`/`vote`/…):
  `eliminateFinalTheme`, `submitWager`, `submitFinalAnswer`, `finalVote` — каждый просто строит
  соответствующий `EngineEvent` и вызывает `dispatch()`.
- Никакой новой транспортной логики уровня фальстарта или грейс-исключения не требуется: в финале
  нет гонки нажатий, весь тайминг — обычное «событие или истечение таймера», которое движок уже умеет
  сам.
- `toGameStateView(viewerId)` расширяется тем же паттерном персональных состояний, что уже применён
  к `correctAnswer`: чужие ставки и ответы не видны никому до `final-reveal` — виновник этого правила
  тот же, что и у ведущего в базовом раунде (design.md, «СУДЕЙСТВО»): если бы каждый видел ставки
  соперников заранее, азарт тайной ставки пропадал бы. Исключение — ведущий на `final-judging`: ему
  нужно видеть ставки и ответы всех, чтобы судить.

## Протокол (`server/src/protocol.ts`)

Клиент → сервер:

```ts
| { type: 'eliminate-final-theme'; themeIndex: number }
| { type: 'submit-wager'; amount: number }
| { type: 'submit-final-answer'; text: string }
| { type: 'final-vote'; participantId: string; correct: boolean } // панель ведущего
```

`GameStateView` — новые поля, заполненные только в финальных фазах:

```ts
finalThemes: { name: string; eliminated: boolean }[] | null; // видно всем начиная с final-elim
finalElimParticipantId: string | null; // чей ход вычёркивать
finalQuestion: { text: string } | null; // видно с final-answer (на final-wager известно только имя темы — finalThemes)
// Персональные, тем же паттерном что correctAnswer: обычному игроку — только ЕГО ставка/ответ (или
// null, пока не отправил); ведущему на final-judging — ставки+ответы ВСЕХ; всем — на final-reveal.
finalWagers: { participantId: string; amount: number }[] | null;
finalAnswers: { participantId: string; text: string }[] | null;
finalVerdicts: { participantId: string; correct: boolean }[] | null;
```

## Клиенты

**Игрок (`/`)**, по фазе:

| Фаза                          | Я                                                                     | Не я / все                             |
| ----------------------------- | --------------------------------------------------------------------- | -------------------------------------- |
| `final-elim`, мой ход         | Список оставшихся тем — тап вычёркивает                               | Список тем, подсвечен тот, чья очередь |
| `final-wager`                 | Название оставшейся темы, поле ввода ставки (`0`..мой счёт), «Готово» | То же                                  |
| `final-answer`                | Текст вопроса, поле ввода ответа, «Готово»                            | То же                                  |
| `final-judging`, я не ведущий | «Ведущий проверяет ответы…»                                           | То же                                  |
| `final-judging`, я ведущий    | Список: игрок / ставка / ответ / кнопки «Верно»/«Неверно»             | —                                      |
| `final-reveal`                | Таблица: игрок — ставка — ответ — вердикт — итоговые очки             | То же                                  |

Панель ведущего (±очки, отмена вопроса), постоянно видимая в базовом раунде, в финальных фазах не
показывается: «отменить вопрос» не имеет смысла (вопрос один и он и есть финал), а точечная правка
очков в разгар отсева/ставок только путала бы — после `final-reveal` счёт уже окончательный (партия
сразу заканчивается), поправить нечего.

**Табло (`/board`)**: `final-elim` — список тем без цены, вычеркнутые зачёркнуты, подсвечена
текущая очередь; `final-wager`/`final-answer` — название темы и текст вопроса, без чужих
ставок/ответов (не видны никому, кроме ведущего — см. «Комната»); `final-reveal` — та же итоговая
таблица, что и у игроков.

## Тестирование

Тем же способом, что и раньше: юнит-тесты движка прогоняют финал целиком — отсев (включая тайм-аут
хода), ставки (включая зажим по `[0, max(0, score)]` и тайм-аут), ответы (включая тайм-аут),
судейство (включая тайм-аут с незачётом по умолчанию), переход в `game-end`, а также оба случая
пропуска финала (нет `pack.final`; `hostId === null`). Комната — интеграционные тесты через настоящие
WS-клиенты, включая обрыв связи и реконнект по токену посреди финала (ничего нового придумывать не
нужно — та же механика токена, что и везде). Один сценарий E2E — отдельным пунктом плана реализации,
не здесь.

## Отказы

Ничего нового сверх уже решённого в исходной спеке и base-round-design.md: любая финальная фаза с
таймером не ждёт человека бесконечно (см. выше — у каждой фазы есть тайм-аут с чётким дефолтом).
Реконнект по токену работает как и раньше: уже отправленные ставка/ответ/вердикт живут в
`EngineState`, а не на клиенте, и не теряются при обрыве связи. Снапшот на диск переживает падение
сервера так же, как и в любой другой фазе — `EngineState` целиком проходит через `JSON.stringify`,
новые поля (плоские `Record`/`number`/`string | null`) этому не мешают.
