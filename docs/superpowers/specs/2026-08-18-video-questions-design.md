# Вопросы с видео (YouTube-эмбед)

Вторая часть идеи «Медиа-вопросы» из `docs/ideas.md`, после картинок
(`2026-08-16-photo-questions-design.md`). Закрывает сразу и видео, и то, что раньше
обсуждалось как отдельные «аудио-вопросы» — оба варианта используют один и тот же механизм,
живой эмбед YouTube-плеера, см. «Источник видео и правило поиска» ниже про причину такого
объединения. Разница между «видео-вопросом» и «аудио-вопросом» — только в том, что видно на
табло: полноценный видеоряд или нейтральная заглушка поверх звука (см. «Сервер и клиент»,
`audioOnly`) — источник и способ проигрывания те же. AI-генерация изображений (портретный
раунд) вопроса не касается и остаётся отдельной, отложенной идеей.

## Правило

Видео допускается только в одном из двух случаев — та же дисциплина, что уже действует для
картинок (`photo-questions-design.md`, «Правило»):

1. **Целый раунд/тема видео-вопросов.** Ролик — само содержание вопроса: «что за фильм?»,
   «что за песня?», «что за сцена?». Текст вопроса минимален.
2. **Точечное видео в обычном раунде — только если без него вопрос нельзя нормально
   задать.** Не украшение и не подсказка. Если вопрос прекрасно работает как текстовый или
   как картиночный — видео не нужно; видео оправдано только там, где важно именно движение
   или звук во времени (сыгранная мелодия, узнаваемая интонация реплики, движение).

Отдельно от «где вообще нужно видео» — генератор решает, **виден ли сам ролик** или только
звук (`audioOnly`, см. «Формат пакета»). Вопрос «что за фильм?» по кадру — видео целиком,
видеоряд и есть содержание. Вопрос «что за песня?» — почти всегда `audioOnly`: если показать
видеоклип, узнавание идёт по картинке, а не по музыке, и вопрос перестаёт быть тем, чем
задуман.

## Источник видео и правило поиска

Генератор ищет ролик сам, без участия человека — но **ничего не скачивает**. Вместо файла в
паке хранится ссылка на публичный YouTube-ролик и таймкод; воспроизведение происходит прямо
во время партии через официальный встроенный плеер (YouTube IFrame Player API).

**Почему не self-hosted, как картинки.** Для картинок легальный бесплатный источник
(Wikimedia Commons/Openverse) реально покрывает большую часть нужных сюжетов. Для видео и
особенно музыки это не так — популярные фильмы и песни физически не существуют в виде
свободно лицензированных файлов, и подделывать источник (искать «похожий», не тот самый) —
не вариант: вопрос должен быть про настоящий фильм/песню, а не про его подобие. Живой эмбед
решает эту проблему в принципе: ролик никогда не копируется и не покидает YouTube, только
воспроизводится с официального сервиса — ровно то же самое действие, что открыть YouTube и
нажать play. Это же снимает разницу между «видео-вопросом» и «аудио-вопросом» — оба
одинаково хорошо решаются одной ссылкой на YouTube-ролик, отдельный механизм для аудио не
нужен.

**Проблема проверки.** Для картинок генератор смотрит на скачанный файл сам, прежде чем его
принять (тот же приём, которым ловятся нерелевантные результаты поиска). Для видео эта
проверка недоступна — генератор не может посмотреть или прослушать ролик. Вместо этого —
**проверка по независимой текстовой корроборации**, не по самому ролику:

1. Сформулировать поисковый запрос по предмету вопроса (не по формулировке вопроса целиком),
   как и для картинок.
2. Найти подходящий публичный YouTube-ролик через веб-поиск.
3. Подтвердить нужный момент **независимым источником** — таймкоды/главы в самом описании
   видео (чтение страницы видео — обычный веб-запрос, не скачивание потока), статья, фан-вики,
   официальное описание. Собственное описание видео само по себе не считается независимым
   подтверждением — совпадение по названию/описанию ролика недостаточно, нужен второй,
   отдельный источник, называющий именно этот момент.
4. Проверить через `oEmbed` YouTube (`https://www.youtube.com/oembed?url=...&format=json`,
   без API-ключа) — ролик существует, публичный, встраиваемый. Отсекает удалённые,
   приватные и недоступные для эмбеда видео ещё на этапе генерации, до того как что-либо
   записано в пак.
5. Если независимой корроборации не нашлось — **не гадать**. Вопрос переписывается в чисто
   текстовый вариант (то же содержание, без `video`), как и с картинками. В финальном отчёте
   генерации (Шаг 6/7 `pack-generator/SKILL.md`) — отдельный список вопросов, для которых
   задумывалось, но не нашлось видео.

Это более строгий и медленный процесс, чем для картинок (там достаточно один раз
посмотреть) — ожидаемо меньшая доля вопросов раунда реально получит видео по сравнению с
тем, как почти все получали картинки в картиночном раунде. Это осознанный компромисс:
недостоверный, но эффектный видео-вопрос хуже отсутствующего.

## Формат пакета

`Question` (`server/src/pack.ts`) получает новое необязательное поле, отдельное от `image`
(вопрос использует либо картинку, либо видео, не оба сразу — тем же собственным суждением
генератора, что уже применяется к выбору картинка/текст):

```ts
video?: {
  youtubeId: string; // идентификатор видео, например "dQw4w9WgXcQ"
  startSeconds: number; // с какой секунды начинать
  durationSeconds: number; // сколько секунд играть, затем плеер сам остановится
  audioOnly?: boolean; // true — на табло не показывать сам ролик, только звук
}
```

Никакого файла на диске — `packs/media/` эта веха не трогает вообще. Весь вопрос целиком —
три значения в JSON пака, ничего не скачивается ни при генерации, ни при игре.

`validatePack`/`validateQuestion` — `video`, если есть: `youtubeId` непустая строка,
`startSeconds` и `durationSeconds` — неотрицательные конечные числа, `durationSeconds` > 0.
Никакой сетевой проверки здесь — `pack.ts` используется живым игровым сервером на каждой
загрузке пака, сетевой запрос на каждый вопрос при каждом старте сервера неприемлем (тот же
принцип, что уже действует для отсутствия проверки файла картинки в `pack.ts`).

## Сервер и клиент

**`GameStateView.currentQuestion`** получает новое поле:

```ts
video: {
  youtubeId: string;
  startSeconds: number;
  durationSeconds: number;
  audioOnly: boolean;
} | null;
```

Строится там же, где уже строятся `text`/`image` для текущего вопроса, той же видимостью:
`null`, пока получатель ещё не определён (cat-handoff/торги аукциона), заполнено — как
только вопрос открыт.

**Показывается только на табло**, тем же решением и по той же причине, что и картинки
(`photo-questions-design.md`, «Сервер и клиент») — здесь причина даже сильнее: если бы
несколько телефонов одновременно попытались проигрывать один и тот же ролик, это была бы
какофония из рассинхронизированного звука с нескольких устройств сразу.

**API грузится заранее, плеер создаётся заранее.** Первая живая проверка (2026-08-18)
показала, что откладывать всё до клика нельзя: `<script>` IFrame API вставлялся только по
нажатию «Играть», и загрузка скрипта, создание плеера и буферизация ролика шли
последовательно уже после него — задержка была заметной, и всё это время шёл таймер вопроса.
Поэтому скрипт грузится один раз при монтировании табло, а плеер создаётся в момент, когда
вопрос вошёл в фазу проигрывания медиа (см. «Фаза проигрывания медиа») — к началу
воспроизведения ролик уже забуферизован.

Плеер создаётся с:

- доменом `https://www.youtube-nocookie.com` (официальный режим повышенной
  конфиденциальности — не ставит трекинг-куки, пока зритель не начал взаимодействовать с
  плеером);
- `playerVars: { start: startSeconds, rel: 0, modestbranding: 1, autoplay: 1 }`.

**Попытка автозапуска, кнопка — запасной путь.** Кнопка как единственный способ запустить
ролик неудобна вживую: табло стоит у телевизора, тыкать в него мышью посреди партии никто не
хочет. Плеер пытается заиграть сам. Если браузер заблокировал автозапуск со звуком (политика
autoplay требует пользовательского жеста на странице, а на табло его может не быть вовсе),
плеер не перейдёт в состояние «играет» — тогда, и только тогда, табло показывает кнопку
«▶ Играть»; сам клик и есть недостающий жест.

**Конец клипа табло отслеживает само, без `playerVars.end`.** `end` — документированный
параметр, но на живой проверке ролик на заданной секунде не остановился. Вместо него табло
опрашивает `getCurrentTime()` и само останавливает воспроизведение по достижении
`startSeconds + durationSeconds`. Это надёжнее и всё равно необходимо по другой причине:
момент остановки — это ещё и сигнал «клип доиграл», по которому стартует таймер вопроса.

**Название ролика закрывается оверлеем.** `rel: 0` и `modestbranding: 1` — официальные
параметры, но с честной оговоркой: `rel=0` с 2018 года ограничивает похожие видео только тем
же каналом, не убирает их полностью; `modestbranding` в актуальном плеере почти не имеет
эффекта (устарел по документации Google). На живой проверке заголовок YouTube, который
показывается поверх кадра в первые секунды воспроизведения и при наведении, прямо выдал
ответ на вопрос. Настройками эмбеда это не лечится, поэтому лечится на своей стороне:
непрозрачная полоса поверх верхней зоны плеера, где живёт заголовок, плюс
`pointer-events: none` на всём эмбеде — тогда ни заголовок, ни контролы не появляются по
наведению, а случайный клик не открывает YouTube. Плата за это — собственные элементы
управления плеера становятся недоступны, то есть пауза и перемотка руками больше не
предполагаются: клип короткий и играет один раз. Всё описанное в этом абзаце — поведение для
обычного видео-вопроса, когда `audioOnly` не установлен.

**Когда `audioOnly: true`** — плеер всё равно создаётся и играет (звук идёт по тому же
IFrame API), но сам `<iframe>` визуально спрятан (сжат/скрыт CSS-ом так, чтобы браузер не
приостанавливал воспроизведение — `display: none` для этого не годится, нужен приём вроде
нулевых размеров с `overflow: hidden`, а не полное исключение из раскладки). На его месте —
нейтральная статичная заглушка, никак не намекающая на содержание ролика: одна и та же
картинка волны звука (`client/src/assets/sound-wave.gif`, положена вручную — не найдена и
не скачана генератором, см. «Отказы») для всех audioOnly-вопросов пака, импортируется как
обычный клиентский ассет через Vite, отдельно ни в один пак не упаковывается.

`image` и `video` — независимые необязательные поля, ничем не запрещающие совпасть на одном
вопросе технически, хотя по правилу генератора вопрос выбирает ровно один тип медиа (см.
«Правило»). На случай, если это правило всё же нарушено — `Board.tsx` детерминированно
отдаёт приоритет `video`, если оно есть (картинка не рендерится вместе с ним); это защитное
поведение на непредусмотренный по дизайну случай, не ожидаемый штатный сценарий.

## Фаза проигрывания медиа

Главное, что вскрыла живая проверка: таймер вопроса (30 секунд) запускался вместе с
открытием вопроса и тикал, пока ролик грузился и играл. На 8-секундном клипе игрок терял
треть времени на размышление ещё до того, как увидел вопрос целиком.

Появляется **новая фаза `question-media`**: вопрос уже открыт и виден, ролик играет, но
таймер вопроса ещё не запущен и кнопка «Ответ» не доступна никому. Клип досматривают
целиком — узнавший с первого кадра не лишает остальных просмотра. Когда клип доиграл, фаза
становится обычной `question-open`, и только тогда стартуют полные 30 секунд.

Вход в `question-media` — только там, где вопрос открывается **впервые**: обычный выбор
вопроса, назначение «кота», победа в торгах аукциона. Переоткрытие после неверного ответа при
ведущем (`resolveVote`) идёт сразу в `question-open`: ролик уже смотрели, второй раз он не
играет, а остаток времени считается по прежнему правилу Комнаты. Вопросы без `video` эту
фазу не проходят вовсе — картинки как были, так и остаются в `question-open` со сразу идущим
таймером.

**Сигнал «клип доиграл» приходит событием**, ровно как «истёк таймер N» — инвариант 1 не
страдает: движок по-прежнему не знает ни про сеть, ни про часы, ни про YouTube. Шлёт сигнал
табло, по собственному отслеживанию `getCurrentTime()` (см. «Сервер и клиент»). Табло не
участник партии — оно никогда не делает `join`, — поэтому сообщение устроено как уже
существующие `admin-*`: без привязки к личности отправителя. Движок принимает его только в
фазе `question-media`, в любой другой это молчаливый no-op, так что ни второе открытое табло
со своим дублирующим сигналом, ни опоздавший сигнал ничего не ломают.

Сигнал несёт **id вопроса**, к которому относится, и движок сверяет его с текущим. Без этого
опоздавший сигнал от предыдущего вопроса оборвал бы клип следующего: сценарий редкий (сигнал
задержался, страховочный таймер успел сработать, следующий вопрос тоже оказался с видео), но
защита от него стоит одного сравнения строк.

**Страховочный таймер.** Если сигнала нет — табло закрыли, сеть отвалилась, ролик не
загрузился, автозапуск не сработал и кнопку никто не нажал — партия обязана поехать дальше
сама. У фазы `question-media` есть собственный таймер; по его истечении движок переходит в
`question-open` ровно так же, как по «клип доиграл». Он заведомо щедрый — заметно больше
самого длинного разумного клипа: это аварийный выход, а не рабочий сценарий, и в нормальной
партии срабатывать не должен. Фаза попадает и в `PHASE_TIMER` Комнаты — иначе партия,
пережившая перезапуск сервера прямо в этой фазе, зависла бы навсегда.

**На телефонах в это время** — тот же экран, что и при открытом вопросе, но без кнопки
«Ответ» и без обратного отсчёта: короткая подсказка, что идёт ролик и отвечать пока рано.

## Валидация при генерации

`server/scripts/validate-pack.ts` получает мягкую дополнительную проверку, параллельную
проверке файлов картинок: для каждого вопроса с `video` — запрос к `oEmbed` YouTube,
подтверждающий, что ролик всё ещё существует и доступен для эмбеда. Недоступный ролик —
**предупреждение**, не ошибка: пак всё равно считается прошедшим проверку. Это отдельная
проверка от той, что генератор уже делает на Шаге поиска (см. выше) — здесь она страхует от
ролика, который стал недоступен уже **после** генерации (удалён, стал приватным) к моменту,
когда кто-то прогоняет валидатор перед игрой.

## Инвариант, который эта веха меняет

Инвариант 3 генератора (`pack-generator/SKILL.md`) расширяется в третий раз: картинки →
видео. Отдельного «аудио» как самостоятельного типа не появляется — см. «Источник видео»
выше.

## Тестирование

**Код (`pack.ts`, `protocol.ts`, `server.ts`, `Board.tsx`)** — тем же способом, что и
`image`: `video` как ещё одно необязательное поле в существующих тестах
`validatePack`/`loadPack`, `currentQuestion.video` в тестах `toGameStateView`, видимость
`null` во время cat-handoff/аукциона — тот же паттерн, что уже покрыт для `image`/`text`.
Рендер кнопки «Играть» и переход в плеер по клику — в `Board.test.tsx`, с замоканным
глобальным `YT`/IFrame API (тест не грузит реальный скрипт YouTube и не делает сетевых
запросов).

**Фаза `question-media`** — там же, где уже живут тесты остальных фаз движка, и по той же
причине, по которой они там живут: движок чист, поэтому вся эта механика проверяется без
единого настоящего таймера и без сети. Что должно быть покрыто: вопрос с `video` уходит в
`question-media`, а без `video` — сразу в `question-open`; «клип доиграл» переводит в
`question-open` и запускает таймер вопроса; тот же сигнал в любой другой фазе не делает
ничего; страховочный таймер даёт тот же результат, что и сигнал; переоткрытие после неверного
ответа при ведущем медиа-фазу не проходит; «Ответ» в `question-media` не принимается.
Отдельно — восстановление из снапшота в этой фазе (`PHASE_TIMER`), тем же тестом, каким
покрыты остальные фазы: иначе зависание после перезапуска сервера никто не поймает.

**`oEmbed`-проверка в `validate-pack.ts`** — интеграционный тест с замоканным `fetch`
(успешный ответ → нет предупреждения, ошибка/404 → предупреждение в выводе), тот же паттерн,
что уже используется для проверки файлов картинок.

**Поиск/корроборация видео генератором** не тестируется юнит-тестами — агентный процесс, не
код в репозитории. Проверяется живым прогоном и разбором результата, как и весь остальной
генератор (`docs/pack-generator-profile.md`).

**Живой тестовый пак — начинать с одного вопроса, не с полного пака.** В отличие от
картиночной вехи (где сразу собирался полный пак на 50 вопросов), поиск с независимой
корроборацией заметно медленнее и дороже. Первый прогон — один пак с ровно одним
видео-вопросом; только если результат устраивает — переходить к паку побольше.

## Отказы

**Ролик стал недоступен между генерацией и игрой** (удалён, стал приватным,
регионально заблокирован). `validate-pack.ts` ловит часть таких случаев заранее (см.
«Валидация при генерации»), но не гарантированно — сеть на момент проверки не гарантирует
сеть/доступность в день партии. Плеер должен обработать `onError` события IFrame API и
показать понятное «видео недоступно» вместо сломанного эмбеда.

**Нет интернета на площадке во время игры.** В отличие от картинок, видео **не работает
офлайн** — принципиальное отличие от self-hosted подхода, стоит явно предупреждать при
выборе пака с видео-раундом (см. `svoya-igra-dev/SKILL.md`, «Ловушки» — изоляция
клиентов/отсутствие сети уже отмечена как известный риск площадки, эта веха его усиливает
для паков с видео).

**Не найдена независимая корроборация таймкода ни для одного кандидата.** Вопрос остаётся
текстовым, без блокировки генерации — см. «Источник видео» выше.

**Заглушка для `audioOnly` (`sound-wave.gif`) положена в репозиторий вручную, не найдена
генератором.** Это единственное исключение из правила «генератор ищет всё сам» — свободных
лицензированных гифок-заглушек в Wikimedia Commons/Openverse на практике не нашлось (обе
библиотеки — в основном энциклопедический контент, не банк UI-иконок), а любой другой
источник в интернете (Giphy, Tenor и т.п.) в подавляющем большинстве не даёт прав на
переиспользование. В отличие от картинки/видео к конкретному вопросу (пересоздаётся каждый
раз генератором), это один статичный ассет на весь клиент — разумно завести один раз вручную
и переиспользовать, а не решать эту проблему для каждого пака заново.

**Название ролика видно поверх кадра и при наведении.** Подтвердилось живой игрой:
`modestbranding` не помогает, заголовок выдал ответ. Закрывается оверлеем и
`pointer-events: none` — см. «Сервер и клиент». Остаточная часть риска: полностью
контролировать чужой эмбед нельзя, и если YouTube поменяет вёрстку плеера, оверлей может
перестать попадать по заголовку. Это проверяется глазами на живом прогоне, а не тестом —
тест видит замоканный `YT`, а не настоящую вёрстку.

**Табло не прислало «клип доиграл».** Закрыли вкладку, отвалилась сеть, ролик не загрузился,
автозапуск не сработал и кнопку никто не нажал. Партию вытаскивает страховочный таймер фазы
`question-media` — см. «Фаза проигрывания медиа». Отдельно: при ошибке загрузки ролика
(`onError` IFrame API) табло не ждёт этот таймер, а сообщает «клип доиграл» сразу — вопрос
становится обычным текстовым, и партия идёт дальше без паузы на пустом месте.
