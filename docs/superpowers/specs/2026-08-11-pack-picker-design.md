# Выбор пакета через UI — дизайн

Продолжение вехи 3 (`docs/superpowers/specs/2026-08-09-pack-generator-design.md`), явно
вынесенное из неё как отдельный design-цикл: «Как сгенерированный пакет становится тем, во
что реально играют — не часть этой вехи... Правильное решение — выбор пакета прямо в
интерфейсе». Это тот выбор.

## Зачем

Сейчас активный пакет — жёстко `PACK_PATH` (по умолчанию `packs/current.json`), заданный при
старте процесса через переменную окружения. Чтобы сыграть другим пакетом, нужно останавливать
сервер и перезапускать его с другим `PACK_PATH` — неудобно и не то, что должен делать человек
за столом посреди вечера.

## Инварианты, которые эта веха не трогает

Уже сегодня `Room.pack` (какой пакет использует **следующая** партия) и `EngineState.pack`
(какой пакет использует **уже идущая** партия) — разные поля. `EngineState.pack`
устанавливается один раз в `createInitialState()` при `startGame()` и с тех пор живёт как
часть игрового состояния, включая при восстановлении из снапшота после перезапуска сервера
(снапшот сериализует весь `EngineState`, значит и вложенный в него `pack` — бесплатно, без
дополнительной работы). Смена `Room.pack` **не может** повлиять на уже идущую партию — она
воздействует только на следующий вызов `startGame()`.

Из этого следует: **менять активный пакет можно в любой момент**, даже посреди чужой партии
— это не потребует ни блокировок, ни предупреждений о «партия в процессе».

## Формат пакета

`Pack` (`server/src/pack.ts`) получает новое **необязательное** поле:

```ts
export interface Pack {
  title: string;
  author: string;
  createdAt: string;
  description?: string; // новое — короткая подпись для быстрого выбора в списке
  rounds: Round[];
  final?: { themes: FinalTheme[] };
}
```

`validatePack` принимает `description`, если оно есть, как строку (тем же способом, что и
`comment?` у вопроса) — отсутствие поля не делает пакет невалидным, старые пакеты (включая
`packs/current.json`) остаются рабочими без изменений.

`.claude/skills/pack-generator/SKILL.md` (Шаг 6, сборка объекта пакета) дополняется: теперь
пишет и `description` — одно предложение по темам пакета. Без этого у сгенерированных
пакетов не было бы описания, и весь смысл списка с описаниями терялся бы именно там, где он
нужнее всего.

## Откуда берётся список пакетов

Новый модуль `server/src/packs.ts`:

```ts
export interface PackSummary {
  filename: string;
  title: string;
  description: string | null;
}

export async function listAvailablePacks(dir: string): Promise<PackSummary[]>;
```

Читает все `*.json` в `dir`, для каждого — `readFile` + `JSON.parse` + уже существующий
`validatePack`. Невалидные (битый JSON, не проходит `validatePack`) — тихо пропускаются, с
`console.error` на сервере для диагностики: список в интерфейсе не должен показывать файл,
который всё равно нельзя выбрать, но и не должен ронять всю выдачу из-за одного плохого
файла.

`dir` — не новая переменная окружения, а `dirname(PACK_PATH)`: `PACK_PATH` уже указывает
внутрь нужной папки, заводить второй способ её задать незачем.

Список **не обновляется автоматически** (ни `fs.watch`, ни поллинг) — только по явному
действию «Обновить», описанному ниже, и один раз при старте процесса (`index.ts` вызывает
`listAvailablePacks` тем же способом, каким уже вызывает `listLanCandidates`, чтобы список в
интерфейсе не был пустым до первого клика). Это осознанный выбор: автослежение за файлами на
Windows не всегда надёжно, а предсказуемое ручное обновление проще объяснить и проще
починить, если что-то пойдёт не так.

## `Room`

Как и LAN-адрес (`server/src/lan-host.ts`, `Room.getLanInfo`/`setLanAddress`/`onLanChange`),
список пакетов и текущий выбор — **не часть `RoomState`/снапшота**: это факт окружения
(что лежит на диске прямо сейчас), а не игровое состояние, которое нужно пережить между
перезапусками. Отдельная подписка, отдельные поля:

```ts
export interface PackInfo {
  available: PackSummary[];
  activeFilename: string | null;
}

class Room {
  getPackInfo(): PackInfo;
  onPackChange(listener: (info: PackInfo) => void): () => void;

  // requesterId: string | null — null означает «с админ-панели», без проверки
  // личности отправителя (тот же паттерн, что у startGame/resetGame/skipToFinal).
  // Иначе — сверяется с this.hostParticipantId (лобби-флаг: выбор пакета имеет
  // смысл до партии, поэтому это hostParticipantId, а не game.hostId).
  refreshAvailablePacks(requesterId: string | null, packs: PackSummary[]): void;
  selectPack(
    requesterId: string | null,
    filename: string,
    pack: Pack,
  ): { ok: true } | { error: 'not-host' | 'unknown-file' };
}
```

При старте `index.ts` уже загружает пакет по `PACK_PATH` (`loadPack`, как и сейчас) и передаёт
его в конструктор `Room` — конструктор дополнительно принимает **имя файла** этого пакета
(`basename(PACK_PATH)`), чтобы сразу заполнить `activePackFilename` и не показывать «ничего
не выбрано» до первого ручного выбора, хотя партию уже можно начинать тем пакетом, что
загрузился при старте.

`refreshAvailablePacks`/`selectPack` сами не трогают диск — как и остальной `Room`, они
получают уже прочитанные/провалидированные данные, чтение файлов делает `server.ts`.

Возвращаемое значение различает две причины отказа, но наружу, клиенту, идёт только одна из
них. `error: 'not-host'` (`requesterId` не `null` и не совпадает с `hostParticipantId`) —
`server.ts` **не** превращает это в `select-pack-error`, просто ничего не отвечает: клиент,
которому кнопка вообще не должна была быть видна, не должен получать осмысленный ответ на
попытку её всё же нажать (тот же принцип, что у `adjust-score`). `error: 'unknown-file'`
(`filename` не входит в `availablePacks`) — это, в отличие от неавторизованности, легитимный
повод сообщить причину: файл мог исчезнуть или измениться между обновлением списка и
выбором, `server.ts` отвечает `select-pack-error` тому же сокету. Room различает эти два
случая на своём уровне (это нужно для тестируемости и точности), решение, что из этого
показывать клиенту — целиком у `server.ts`.

## Протокол

Два независимых набора сообщений — участник (только ведущий) и админка (без проверки
личности), тем же способом, каким уже разделены `skip-to-final`/`admin-skip-to-final`:

```ts
// ClientMessage, от участника — сервер сам сверяет отправителя с hostParticipantId
| { type: 'refresh-packs' }
| { type: 'select-pack'; filename: string }

// ClientMessage, с админ-панели — без проверки личности
| { type: 'admin-refresh-packs' }
| { type: 'admin-select-pack'; filename: string }
```

```ts
// ServerMessage, добавляется к 'state' (как lanUrl/lanCandidates — живое,
// пересчитывается на каждой рассылке, видно всем подключённым, действовать
// могут только ведущий и админка)
availablePacks: PackSummary[];
activePackFilename: string | null;
```

```ts
// Новое сообщение — попытка select-pack/admin-select-pack на файл, который
// успел стать невалидным или исчезнуть между обновлением списка и выбором.
| { type: 'select-pack-error'; reason: 'unknown-file' }
```

`server.ts`: `refresh-packs`/`admin-refresh-packs` вызывают `listAvailablePacks(PACKS_DIR)` и
передают результат в `room.refreshAvailablePacks(...)`; `select-pack`/`admin-select-pack`
читают и валидируют указанный файл (`loadPack` из `pack.ts`), при успехе — `room.selectPack(...)`,
при неудаче — `select-pack-error` тому же сокету, без широковещательной рассылки (как
`start-game-error`).

## Интерфейс — два места

**`Admin.tsx`** — новая секция «Пакет», тем же паттерном, что уже есть секция «Сеть»: список
`availablePacks` (название + описание, если есть), кнопка «Обновить», текущий выбранный —
выделен и задизейблен, клик по другому — `admin-select-pack`.

**`Player.tsx`** — тот же список и кнопка «Обновить», но не в игровой панели ведущего
(`hostAdminPanel()`, рендерится только пока `game` не `null`), а в лобби-блоке (там, где
сейчас «Стать ведущим» / «Начать игру», рендерится при `!game`), и только когда
`isHost === true`. Выбор пакета имеет смысл до партии — там ему и место; в игровой панели
ведущего его размещать незачем, она в принципе не существует до `startGame()`.

`useRoomConnection.ts` и `useAdminConnection.ts` получают `availablePacks`,
`activePackFilename`, `selectPackError`, `refreshPacks()`, `selectPack(filename)` —
симметрично тому, как `useAdminConnection.ts` уже получил `lanCandidates`/`setLanAddress`.

## Тестирование

Тот же паттерн, что и LAN-адрес: юнит-тесты на `packs.ts` (валидные/невалидные/пустая папка),
юнит-тесты на `Room` (refresh/select, авторизация — с `null`, с правильным и неправильным
`requesterId`), интеграционные тесты на `server.ts` (сообщения по реальному сокету, включая
`select-pack-error`), компонентные тесты на `Admin.tsx`/`Player.tsx` (список, кнопка,
клик, видимость только для `isHost`).

## Отказы

**Невалидный или отсутствующий пакет в момент выбора.** `select-pack-error`, клиент
показывает причину, ничего не меняется.

**Не ведущий и не админка пытается выбрать пакет.** Тихий no-op — по протоколу такое
сообщение в принципе не должно было уйти (кнопка не показана), поэтому не отдельный
пользовательский сценарий, а просто защита на сервере.

**Партия уже идёт, а пакет меняют.** Не отказ, а штатный сценарий — см. «Инварианты, которые
эта веха не трогает» выше: не влияет на уже идущую партию.
