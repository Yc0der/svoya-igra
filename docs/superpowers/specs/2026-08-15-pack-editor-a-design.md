# Ручной редактор пакетов — Веха A (просмотр/правка/удаление вопросов)

Идея из `docs/ideas.md` («Ручной редактор пакетов»), одобрена в брейнсторминге 2026-08-15.
Разбита на вехи при брейнсторминге — эта спека описывает только первую:

- **Веха A (эта спека)** — просмотр пакета, правка существующего вопроса (текст, ответ,
  комментарий, цена, тип), удаление вопроса.
- **Веха B (позже)** — добавление новых вопросов в существующую тему.
- **Веха C (позже, по необходимости)** — структурная правка: темы/раунды целиком, метаданные
  пакета (title/author/description), финал.

Каждая веха играбельна/полезна сама по себе, тем же принципом, что и вехи основной игры
(`.claude/skills/svoya-igra-dev/SKILL.md`).

## Правило

В `/admin`, у каждого пакета в уже существующем списке (`admin-packs`,
`Admin.tsx`/`server/src/packs.ts`) — вторая кнопка «Редактировать» рядом с существующей
кнопкой выбора. Открывает сетку «раунды → темы → цены» того же вида, что видят игроки на
табло (`Board.tsx`) — только здесь кликабельна **любая** цена, понятия «уже отвечен» тут нет.

Клик по цене открывает форму под сеткой: цена, текст, ответ, комментарий (необязательно), тип
(`обычный`/`кот`/`аукцион`), кнопки «Сохранить» и «Удалить». Сохранение сразу перезаписывает
тот же файл пакета на диске — без варианта «всегда писать новый файл», как это делает
генератор (`.claude/skills/pack-generator/SKILL.md`, инвариант 1) — решение принято явно при
брейнсторминге: одновременного редактирования во время уже идущей партии не предполагается, а
если это всё же случится, у уже загруженной в память партии ничего не изменится, пока файл не
перечитают заново (перезапуск сервера или повторный выбор того же файла).

`id` вопроса **не редактируется** — не показывается в форме как поле, только внутренним
идентификатором для сохранения/удаления. Причина: `id` — служебное поле движка
(`answeredQuestionIds`, история хода), редактировать его человеку незачем, а опечатка в нём
может незаметно сломать уникальность на весь пакет.

Тема финала (`pack.final`) и метаданные пакета (`title`/`author`/`description`) в этой вехе
**не редактируются** — только вопросы обычных раундов.

## Инвариант, который эта веха меняет — осознанно

До сих пор пакет-файлы на диске писал только генератор (skill `pack-generator`, отдельный
процесс/навык, не код игры — инвариант 5, «Генератор и игра связаны только форматом файла»).
Эта веха — первый случай, когда **сам игровой сервер** пишет файл пакета. Это не нарушает
инвариант 5 (никакого кодового импорта между сервером и генератором по-прежнему нет, оба
общаются только форматом файла) — но стоит явно отметить сдвиг: «кто пишет пакет-файлы» с
этой вехи включает не только человека и генератор, но и сам сервер через UI.

## Протокол и сервер

Новые admin-only сообщения — тот же паттерн, что уже есть у `admin-select-pack`/
`admin-set-lan-address` (`server/src/protocol.ts`): без проверки личности отправителя, как и
всё остальное на админ-панели.

```ts
| { type: 'admin-get-pack'; filename: string }
| {
    type: 'admin-update-question';
    filename: string;
    questionId: string;
    price: number;
    text: string;
    answer: string;
    comment?: string;
    // Названо questionType, не type — не путать с полем-дискриминантом самого сообщения.
    questionType: 'обычный' | 'кот' | 'аукцион';
  }
| { type: 'admin-delete-question'; filename: string; questionId: string }
```

Ответ сервера — один и тот же тип на все три сообщения, чтобы клиенту не нужно было
по-разному обрабатывать get/update/delete:

```ts
| { type: 'admin-pack'; filename: string; pack: Pack }
| { type: 'admin-pack-error'; filename: string; reason: string }
```

**Проверка `filename`.** Обязан быть уже в `availablePacks` (тот же safety-check, что у
`selectPack` — «unknown-file») — иначе `admin-pack-error`. Список пакетов и так уже содержит
только валидные файлы (`listAvailablePacks` тихо пропускает битые), так что редактор всегда
открывается для уже проверенного файла.

**`admin-update-question`/`admin-delete-question`:**

1. Перечитать файл заново с диска (`loadPack(path)`, `server/src/pack.ts`) — не доверять тому,
   что было в памяти у клиента к моменту клика «Сохранить» (файл мог измениться между
   `admin-get-pack` и сохранением, если открыты две вкладки — маловероятно, но перечитывание
   не стоит ничего и полностью убирает этот случай).
2. Найти вопрос по `questionId` по всем раундам и темам — `id` уникален на весь пакет
   (`checkUniqueQuestionIds` в `pack.ts` это уже гарантирует), поэтому достаточно одного
   плоского поиска, `roundIndex`/`themeIndex` в сообщении не нужны.
   Не найден → `admin-pack-error` («вопрос с таким id не найден»).
3. Применить правку (заменить поля вопроса при update; убрать вопрос из массива темы при
   delete).
4. Прогнать **весь** результат через `validatePack` — не только изменённый вопрос. Дёшево
   (пакет ≤ 50 вопросов) и ловит структурные проблемы вроде опустевшей темы после удаления
   (`validateTheme` требует непустой массив вопросов — `requireArray` бросает понятную
   ошибку). Ошибка валидации → `admin-pack-error` с текстом ошибки как есть (сообщения в
   `pack.ts` уже человекочитаемые по-русски, отдельного перевода не требуется).
5. Записать результат на диск **атомарно** — temp-файл + rename, тот же паттерн, что уже есть
   в `server/src/snapshot.ts` (`writeFileAtomic`). Общий с ним хелпер не выносится в
   отдельный модуль в этой вехе — два похожих, но самостоятельных места, лишняя абстракция
   ради двух вызовов не оправдана (YAGNI).
6. В ответ — свежепрочитанный `admin-pack` **с диска** (не собранный из уже применённой в
   памяти правки) — тот же принцип, что и в п.1: источник истины всегда файл, а не то, что
   сервер только что сам написал.

**`admin-get-pack`:** читает файл (`loadPack`), отвечает `admin-pack` с полным содержимым.

## Клиент

Новый режим в `Admin.tsx` (не отдельный маршрут — просто локальный React-стейт `editingPack:
{ filename: string; pack: Pack } | null`). У каждого пакета в существующем списке — вторая
кнопка «Редактировать» рядом с уже существующей (кнопка выбора пакета остаётся как есть, обе
кнопки в одном `<li>`).

Клик «Редактировать» → `admin-get-pack` → рендерится сетка (переиспользует ту же вёрстку сетки
«раунды → темы → цены», что уже есть в `Board.tsx`/`Player.tsx`'s selecting-фазе, но без
понятия «отвечен» — все цены всегда кликабельны).

Клик по цене → форма под сеткой: `<textarea>` для текста и ответа (не `<input>` — обе строки
бывают длинными, комментарий на игровом экране формата пакета уже подтверждает это —
`docs/superpowers/specs/2026-08-03-svoya-igra-design.md`, «Формат пакета»), `<input
type="number">` для цены, `<select>` для типа.

«Сохранить» → `admin-update-question`. При `admin-pack-error` — текст ошибки прямо в форме
(`role="alert"`, тот же паттерн, что `player-alert`/аналоги в `Admin.tsx`). При успехе —
локальный `editingPack.pack` заменяется на пришедший с сервера, форма закрывается, сетка
обновляется с новыми данными.

«Удалить» → тот же двухтаповый confirm, что уже есть у кнопки «Снести всё» в этом же файле
(`Admin.tsx`, локальный стейт `confirmingWipe`/паттерн «текст кнопки меняется на „Точно?“ при
первом клике») — свой независимый стейт для формы редактирования вопроса, не переиспользует
`confirmingWipe` напрямую (тот привязан к сбросу комнаты, а не к пакетам — разные действия).

«Готово» (или клик по другому пакету в списке) — выход из режима редактирования, `editingPack
= null`, обратно к обычному списку пакетов.

## Тестирование

**Сервер.** Тот же паттерн, что уже разделяет `listAvailablePacks`/`selectPack` в проекте:
чистая логика чтения/записи — в `server/src/packs.ts`, тестируется в уже существующем
`server/src/packs.test.ts` (сейчас там только тесты `listAvailablePacks`); проводка через
протокол/WebSocket — в `server/src/server.ts`, тестируется в уже существующем
`server/src/server.test.ts`.

`packs.test.ts` (новая логика, без сети):

- `admin-get-pack` на известный файл — возвращает содержимое, совпадающее с `loadPack`.
- `admin-get-pack` на файл не из `availablePacks` — `admin-pack-error`.
- `admin-update-question` меняет текст/цену/тип существующего вопроса — файл на диске
  реально изменился (перечитать напрямую, не через `admin-pack`-ответ, чтобы не тестировать
  сервер через самого себя).
- `admin-update-question` с несуществующим `questionId` — `admin-pack-error`, файл на диске
  не изменился.
- `admin-update-question` с пустым `text`/невалидной `price` (например, `0` или
  отрицательная) — `admin-pack-error`, файл не изменился (валидация ловит до записи).
- `admin-delete-question` убирает вопрос — файл на диске подтверждает.
- `admin-delete-question` на последнем вопросе темы — `admin-pack-error`, файл не изменился
  (тема не может остаться пустой).

Отдельного теста на саму атомарность temp+rename не заводим — паттерн копируется с уже
рабочего и непроверяемого этим же способом `writeFileAtomic` в `snapshot.ts` (там его тоже
никто не проверяет через прерывание `rename`, это гарантия самой файловой системы/Node, а не
кода, который стоит перепроверять юнит-тестом).

**Клиент** (`Admin.test.tsx`):

- Клик «Редактировать» показывает сетку с ценами пакета.
- Клик по цене открывает форму с текущими значениями вопроса.
- Сохранение с валидными данными закрывает форму, обновляет сетку.
- Сохранение с ошибкой от сервера показывает текст ошибки, форма остаётся открытой.
- Удаление требует двух кликов (первый — подтверждение, второй — реальное действие).
- «Готово» возвращает к списку пакетов.

## Отказы

**Удаление последнего вопроса в теме.** `validatePack` и так требует непустой массив
вопросов у темы — сервер отклонит с понятной ошибкой. Убрать тему целиком — вне этой вехи
(Веха C).

**Правка пакета, который прямо сейчас идёт в игре.** Не обрабатывается специально — решение
при брейнсторминге: уже загруженная в память партия правку на диске не увидит, пока файл не
перечитают заново.

**Параллельное редактирование с двух вкладок админки одновременно.** Не рассматривается —
один ведущий, один ноутбук. Перечитывание файла перед каждой правкой (см. «Протокол и
сервер», п.1) страхует от самого грубого случая (устаревшие данные в форме), но не от гонки
двух одновременных сохранений — это осознанно вне скоупа.

**Файл, не прошедший валидацию, недоступен для редактирования.** Список редактируемых
пакетов — тот же `availablePacks`, что уже есть; совсем сломанный файл по-прежнему чинится
вручную в текстовом редакторе, эта веха работает только с уже валидными пакетами.
