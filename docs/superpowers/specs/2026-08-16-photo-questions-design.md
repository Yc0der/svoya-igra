# Вопросы с картинками (фото из интернета)

Первая часть идеи «Медиа-вопросы» из `docs/ideas.md` — только картинки, только фото,
найденные и скачанные генератором из интернета. Аудио, видео и AI-генерация изображений —
отдельные, отложенные идеи (см. `docs/ideas.md`, «Медиа-вопросы» и «AI-портретный раунд»).

## Правило

Картинка допускается только в одном из двух случаев — генератор обязан явно определить,
какой именно, прежде чем прикреплять картинку к вопросу:

1. **Целый раунд/тема картиночных вопросов.** Картинка — само содержание вопроса, не
   иллюстрация к нему: «что за цветок на картинке?», «кадр из какого фильма/музыкального
   клипа?». Текст вопроса минимален (обычно один короткий уточняющий вопрос), вся
   содержательная часть — в картинке.
2. **Точечная картинка в обычном раунде — только если без неё вопрос нельзя нормально
   задать.** Не украшение и не подсказка, срезающая путь к ответу: если вопрос прекрасно
   работает как чисто текстовый — картинки не будет. Годный пример: вопрос про визуальный
   паттерн (созвездие, герб, флаг с редким сочетанием цветов), который иначе пришлось бы
   неуклюже и неточно описывать словами.

**Годный пример vs брак.** «Какой газ самый распространённый в атмосфере Земли?» с
картинкой земной атмосферы — брак: картинка ничего не добавляет, вопрос и так самодостаточен
текстом. «Флаг какой страны здесь изображён?» с картинкой этого флага — годно: без картинки
вопрос вообще не имеет смысла.

На Шаге 6 (финальная проверка, `pack-generator/SKILL.md`) добавляется отдельная сверка:
у каждого вопроса с картинкой должен быть явный ответ на вопрос «это раунд картинок, или
картинка обязательна для смысла вопроса?» — если ответ «просто показалось, что было бы
красиво» — картинку убрать. Это тот же класс брака, что уже описан в
`pack-generator-profile.md` для калибровки сложности: картинка-подсказка, которая делает
вопрос слишком лёгким или необязательным, такая же ошибка, как цена 400 за общеизвестный
факт.

## Источник картинок и правило поиска

Генератор ищет и скачивает картинку сам — без участия человека (решение при
брейнсторминге). Источники, по порядку:

1. **Wikimedia Commons** (`commons.wikimedia.org`, публичный API MediaWiki, без ключа) —
   основной источник. Почти всё под CC/public domain, и для фактических вопросов (флаги,
   памятники, животные, исторические личности) там обычно есть точная релевантная картинка.
2. **Openverse** (`api.openverse.org`, публичный API, без ключа) — резервный источник, если
   Commons не дал ничего подходящего. Агрегирует свободно лицензированный контент из
   нескольких источников, включая сам Wikimedia Commons и Flickr CC.

Unsplash/Pexels/Pixabay **не подключаются в этой вехе** — их API требуют регистрации и
ключа, которых сейчас нет. Остаётся будущим расширением, если покрытия Wikimedia+Openverse
окажется недостаточно на практике.

**Процесс на вопрос, для которого решено добавить картинку:**

1. Сформулировать поисковый запрос по сути вопроса/ответа (не по формулировке вопроса
   целиком — по предмету: «Эйфелева башня», не «что это за сооружение в Париже»).
2. Запросить Wikimedia Commons API (`action=query&generator=search&gsrnamespace=6`,
   `prop=imageinfo&iiprop=url`) — взять первый разумный кандидат.
3. Если ничего подходящего — тот же запрос в Openverse API (`api.openverse.org/v1/images/`).
4. Скачать кандидата в `packs/media/<имя-пака-без-.json>/<slug-предмета>.<расширение>`
   (создать директорию при необходимости).
5. **Посмотреть на скачанную картинку** (генератор умеет читать изображения) — убедиться,
   что она действительно соответствует вопросу/ответу, а не просто похожа по названию файла
   или совпала по ключевым словам с чем-то посторонним.
6. Если подходит — записать `question.image` (имя файла). Если не подходит — попробовать
   следующего кандидата из того же запроса; после разумного числа попыток по обоим
   источникам — отказаться от картинки для этого вопроса, оставить его чисто текстовым.

**Если картинку найти не удалось**, хотя вопрос задумывался как картиночный — вопрос не
блокирует генерацию, просто переписывается в чисто текстовый вариант (то же содержание, без
`image`). В конце генерации (Шаг 6, итоговый отчёт) — отдельный список вопросов, для которых
задумывалась, но не нашлась картинка, чтобы человек знал об этом.

Об авторстве/лицензии картинки в паке не запоминается — это личная непубличная вечеринка, не
публикация, формальное соблюдение атрибуции не требуется.

## Формат пакета и хранение

`Question` (`server/src/pack.ts`) получает новое необязательное поле:

```ts
image?: string; // имя файла, без пути, например "eiffel-tower.jpg"
```

Путь не хранится в паке целиком — сервер сам разрешает полный путь на диске как
`<packsDir>/media/<имя-файла-пака-без-.json>/<image>`. Так генератору не нужно заранее знать
финальное имя файла пака при записи вопросов, только своё собственное (которое оно и так уже
определяет).

`validatePack`/`validateQuestion` — `image`, если есть, просто непустая строка. Никакой
проверки существования файла на диске здесь: `pack.ts` используется живым игровым сервером
на каждой загрузке пака, и лишний диск-I/O на каждый вопрос каждого пака — не то место для
этой проверки (см. «Валидация при генерации» ниже, отдельный механизм для отдельной цели).

## Сервер и клиент

**Раздача файлов.** Новый статический маршрут — `sirv`, раздающий `<packsDir>/media/`, тот
же паттерн, что уже раздаёт клиентские файлы (`server.ts`). Подключается **до** фолбэка на
клиентский SPA, чтобы `/media/...` не перехватывался клиентским роутингом.

**`GameStateView.currentQuestion`** получает новое поле:

```ts
image: string | null; // готовый относительный URL, например "/media/sport/eiffel-tower.jpg"
```

Строится там же, где уже строятся `text`/`price`/`themeName` для текущего вопроса — тот же
источник данных (загруженный пак), просто ещё одно поле оттуда. Видимость подчиняется тому
же правилу, что уже действует для `text`: `null`, пока получатель ещё не определён (во время
cat-handoff), непустой URL — как только вопрос открыт и текст виден.

**Показывается только на табло** (`Board.tsx`) — телефоны игроков (`Player.tsx`) получают ту
же строку `image` в общем состоянии (поле не персонализировано по получателю), но никогда её
не рендерят и не запрашивают файл — картинка технически видна только на табло. Причина решения
(брейнсторминг): все смотрят на общий экран, телефон — только пульт управления, а не второй
источник картинки, лишняя нагрузка на Wi-Fi без пользы.

`Board.tsx` рендерит `<img>`, когда `currentQuestion.image` не `null` — над/под текстом
вопроса (текст, если есть, никуда не девается — оба поля независимы и могут присутствовать
одновременно, см. «Правило»).

## Валидация при генерации

`server/scripts/validate-pack.ts` (отдельный CLI-скрипт, используемый только на Шаге 6
генерации, не самим игровым сервером) получает мягкую дополнительную проверку: для каждого
вопроса с `image` — существует ли файл `<packsDir>/media/<пак>/<image>` на диске.
Отсутствующий файл — **предупреждение** в вывод скрипта, не ошибка валидации: пак всё равно
считается прошедшим проверку и готовым к игре.

Это в первую очередь страховка на случай будущей ручной правки пака (кто-то вписал `image`
руками, не положив файл) — при штатном автоматическом скачивании к этому шагу файл уже
должен быть на месте, так что в обычном потоке это предупреждение никогда не появляется.

## Инвариант, который эта веха меняет

Инвариант 3 генератора (`pack-generator/SKILL.md`, «Никаких медиа-вопросов. Ни картинок, ни
аудио, ни видео, ни ссылок на файлы, которых не существует. Только текст.») требует правки —
картинки теперь разрешены, при соблюдении правила из этой спеки (раздел «Правило» выше).
Аудио и видео остаются под запретом инварианта — эта веха трогает только картинки.

## Тестирование

**Код (`pack.ts`, `protocol.ts`, `server.ts`, `Board.tsx`)** тестируется тем же способом,
что и остальные поля пака — `image` как ещё одно необязательное поле в уже существующих
тестах `validatePack`/`loadPack`, `currentQuestion.image` в уже существующих тестах
`toGameStateView`/интеграционных WS-тестах, рендер `<img>` в `Board.test.tsx` при наличии
`currentQuestion.image`, отсутствие `<img>` при `null`.

**Статический маршрут `/media/`** — интеграционный тест в `server.test.ts`: положить файл в
temp-директорию, запросить `/media/<файл>` через HTTP, ожидать содержимое файла.

**Поиск/скачивание/проверка картинки генератором** не тестируется юнит-тестами — это
агентный процесс (диалог с человеком через `pack-generator/SKILL.md`), а не код в
репозитории. Правильность проверяется тем же способом, что и весь остальной генератор:
живой прогон и разбор результата (см. `docs/pack-generator-profile.md`), не автоматическим
тестом.

## Отказы

**Скачанная картинка оказалась битой/не загружается в браузере.** Не обрабатывается
специально — деградирует до сломанной иконки картинки в браузере, как любой битый `<img
src>`. Собственная проверка генератора (просмотр картинки перед принятием, см. «Источник
картинок») уже должна ловить это в подавляющем большинстве случаев до попадания в пак.

**Пак с картинками, скопированный на другую машину без папки `packs/media/`.** Пакет
перестаёт быть переносимым одним файлом — при копировании нужно копировать и папку с
медиа. Осознанный компромисс: полная переносимость требовала бы упаковки медиа прямо в JSON
(base64 или подобное), что сломало бы человекочитаемость формата — а она важнее для
существующего рабочего процесса (правка пака в текстовом редакторе, ручной редактор пакетов).

**Не найдена подходящая картинка ни в одном источнике.** Вопрос остаётся текстовым, без
блокировки генерации — см. «Источник картинок» выше.

**Аудио/видео вопросы.** Вне скоупа этой вехи — инвариант 3 для них остаётся в силе.
